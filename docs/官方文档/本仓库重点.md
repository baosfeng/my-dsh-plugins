## 二、官方有、本仓库没碰到 → 读它之前先确认需要

官方 57 个子系统页里，本仓库**完全没碰**的有 39 页：

> `agent-team` · `browser-use` · `client-resources` · `compaction` · `computer-use` · `conversation` · `credentials` · `extensions` · `feedback` · `filesystem` · `invariants` · `jobs` · `lsp` · `mcp` · `permission-presets` · `persistence` · `plan` · `ptc-runtime` · `sandbox` · `schedule` · `scope` · `session-projection` · `session-reference` · `session-telemetry` · `settings` · `shell` · `spill` · `ssh` · `storage` · `subprocess` · `terminal` · `token-meter` · `typert` · `user-questions` · `web` · `webhook` · `workflow` · `workspace` · `core`（agent 创建部分例外，见下）

**部分用到**（用到的部分已在第一节覆盖，其余可跳过）：`core`（仅 `ctx.get('agents').create()` 起子 agent）· `llm-streaming`（仅监听 `llm/stream` 事件，不用 `StreamChunk`）· `client-modules`（只声明 `dsh.client`，不自调）· `todo`（只读 `todo/write` 判未完成）· `attachment`（只转发引用给宿主渲染）· `web-client`（只消费 client 面服务）。

**注意几处同名陷阱**：本仓库的 `sandbox` 命中是 iframe CSP、`schedule*` 是自研调度器、`feedback` 是 UI 文案、`webhook/` 是自研**出站**推送（方向与官方 webhook 相反）——**别据此以为在用官方能力**。

## 三、官方文档答不了：本仓库自研约定（只能看仓库内）

**3.1 自研原语（`plugins/dsh-shared/`，官方无对应物）** —— 细节与禁忌见 [插件资源占用](../踩坑/插件资源占用.md) · [异步落盘与时序](../踩坑/异步落盘与时序.md)：

| 原语                       | 用途                                                | 关键禁忌                                                                      |
| -------------------------- | --------------------------------------------------- | ----------------------------------------------------------------------------- |
| `jsonlAppender`            | JSONL 增量追加 + 阈值 compact                       | **事件流唯一正确原语**                                                        |
| `atomicWriteJson`          | 原子全量快照（tmp+rename，默认 1s 节流 + 1MB 上限） | **事件流禁用**（写放大数百~千倍）；只适用低频全量写                           |
| `createWriteScheduler`     | 防抖 + 最小间隔 + 串行 + drain/flush                | 与 `atomicWriteJson` **双节流互斥**，同开会静默丢状态；写入节奏只能有一个来源 |
| `boundedMap` / `boundList` | 有界容器（LRU/FIFO + 淘汰计数）                     | 不适用事件流/审计日志（淘汰即丢数据）                                         |
| `createResourceGuard`      | 资源看门狗（15s 采样 → 连续 3 次确认降级）          | 只对磁盘类阈值降级，CPU/内存仅告警                                            |
| `isTrustedApiRequest`      | Host-header 信任围栏                                | 12 个插件的 `/api` 都过它                                                     |
| `client-parts/*.part.js`   | Markdown 三级回退、样式单一来源、DOM 接管           | 样式**必须放 `apply` 最前无条件注入**                                         |
| `test-kit/wait.mjs`        | `whenReady`/`waitFor` 确定性等待                    | 禁止固定 sleep 猜时间（门禁 `check-test-sleeps.mjs`）                         |

**3.2 跨插件事件 `plugin:status-query`**（官方无）：`dsh-my-observability` 聚合端点逐个 `ctx.emit`，3s 超时；4 个插件监听并**用完整包名比对自己**后返回 `{ ok, value: { plugin, config(脱敏), running, stats?, lastActions } }`。新插件要出现在聚合面板就必须注册该监听。

**3.3 自造字段（官方无，本仓库约定）**：`dsh.kind`（`library`/`preset`）· `dsh.ui=false` + `dsh.uiReason`（截图门禁豁免）· `dsh.presetReason` · `dsh.client.externalDegraded`。官方 `DshManifest` 只有 `manifestVersion`/`bundle`/`profile`/`client`。

## 四、容易被误导：文档/skill 提到但代码零使用的 API

改代码前若在这些名字上打转，先看这行——**当前仓库没有调用者**：

- `inputMachine` / `facade` 的 insert/consume/remove/subscribe —— 仅见于 `skills/plugin-runtime-debug` 的描述（方法论仍成立，示例已无对应实现）。
- **`ctx.config`** —— 全仓 11 处出现**全在注释里**，真实调用 0；配置入口是 `apply(ctx, config)` 第二实参，且客户端根本访问不到它（改动时别照注释写代码）。
- `ctx.get('slots')` 免 `inject` 动态取服务 —— 14 个 client 插件一律走 `exports.inject`，没有这种写法。
- `settings.plugin.item` / `ctx.settingsScope` / `settings.section` / `installSection` —— 本仓库设置走 `settings.plugins.tab` + localStorage，host 半零使用（这些 slot 官方真实存在，只是本仓库没接）。

## 五、官方文档 vs 本仓库代码冲突时怎么判

1. **语义冲突** → 以**本机运行包**为准：`~/.npm-global/lib/node_modules/@deepseek-ai/*`（读 `*.d.ts` 与 `lib/`）。
2. **用法冲突** → 以**本仓库现有插件**为准（找一个在用的照抄，别照官方示例重写）。
3. 官方 docs 反映 `master`（示例基线 `0.1.6-alpha.1`），本机可能落后——**本机优先**。
4. **实例（不是对错，是用途不同）**：设置页槽位，官方 cookbook 主推 keyed 卡片 `settings.plugin.item` + host 半 `installSection`；本仓库 31 个文件用列表页 `settings.plugins.tab` + localStorage。两者都是官方真实 slot（`slot-catalog.ts` 可查）。

## 七、这份文档怎么维护（改了代码之后）

第一节的能力清单是**从 `plugins/*/src` 取证**得出的派生内容（不是凭记忆写的观点），由门禁 `doc-api`（`scripts/check-doc-api-drift.mjs`）双向守护：**文档提到代码里不存在的 API**、**代码在用而文档没登记**，两者都会变红——别手工凭记忆改。

| 代码改了什么            | 门禁会报什么                    | 你要做什么                                                                   |
| ----------------------- | ------------------------------- | ---------------------------------------------------------------------------- |
| 调用新宿主 API / 新插件 | 报「代码在用的 X 未登记」       | 在第一节表格加一行（能力 / 用途 / 范例 / 官方页）                            |
| 移除或替换某个 API      | 报「文档声明 X 但代码里找不到」 | 改该行；确属"有意标注为不存在"则登记 `INTENTIONALLY_ABSENT` 并在文档写明理由 |
| 发现新陷阱 / 新自研契约 | 不报（事实类）                  | 人工写入第三节；踩坑类事实归 `docs/踩坑/`                                    |

```bash
npm run check:doc-api                                          # 只跑本门禁
npm run verify                                                 # 全量（CI 等价）
npx vitest run --config scripts/test/vitest.config.mjs check-doc-api   # 门禁自测
```

本页只放「从代码派生」的清单与官方页映射；踩坑类事实归 [docs/踩坑/](../踩坑/README.md)。
