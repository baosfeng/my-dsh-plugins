## 三、官方文档答不了：本仓库自研约定（只能看仓库内）

**3.1 自研原语（`plugins/dsh-shared/`，官方无对应物）** —— 细节与禁忌见 [插件资源占用](../踩坑/插件资源占用.md) · [异步落盘与时序](../踩坑/异步落盘与时序.md)：

| 原语                       | 用途                                                | 关键禁忌                                                                      |
| -------------------------- | --------------------------------------------------- | ----------------------------------------------------------------------------- |
| `jsonlAppender`            | JSONL 增量追加 + 阈值 compact                       | **事件流唯一正确原语**                                                        |
| `atomicWriteJson`          | 原子全量快照（tmp+rename，默认 1s 节流 + 1MB 上限） | **事件流禁用**（写放大数百~千倍）；只适用低频全量写                           |
| `createWriteScheduler`     | 防抖 + 最小间隔 + 串行 + drain/flush                | 与 `atomicWriteJson` **双节流互斥**，同开会静默丢状态；写入节奏只能有一个来源 |
| `boundedMap` / `boundList` | 有界容器（LRU/FIFO + 淘汰计数）                     | 不适用事件流/审计日志（淘汰即丢数据）                                         |
| `createResourceGuard`      | 资源看门狗（15s 采样 → 连续 3 次确认降级）          | 只对磁盘类阈值降级，CPU/内存仅告警                                            |
| `isTrustedApiRequest`      | Host-header 信任围栏                                | 15 个插件的 `/api` 都过它（现场取：`grep -rl isTrustedApiRequest plugins/*/src`）                                                     |
| `client-parts/*.part.js`   | Markdown 三级回退、样式单一来源、DOM 接管           | 样式**必须放 `apply` 最前无条件注入**                                         |
| `test-kit/wait.mjs`        | `whenReady`/`waitFor` 确定性等待                    | 禁止固定 sleep 猜时间（门禁 `check-test-sleeps.mjs`）                         |

**3.2 跨插件事件 `plugin:status-query`**（官方无）：`dsh-my-observability` 聚合端点按 `pluginInventory` 清单**逐项查询**、3s 超时；**收集返回值只能用 `serial`**——`emit` 同步派发不收集监听器返回值、`parallel` 只处理异常不返回结果（`Promise<void>`），两者都只会静默拿到 `undefined` 并**编造"运行中"假状态**（实测见[宿主运行时陷阱](../踩坑/宿主运行时陷阱.md)）。5 个插件监听并**用完整包名比对自己**后返回 `{ ok, value: { plugin, config(脱敏), running, stats?, lastActions } }`（现场取：`grep -rl plugin:status-query plugins/*/src`）；无匹配响应如实标记 `no-response`。新插件要出现在聚合面板就必须注册该监听。

**3.3 自造字段（官方无，本仓库约定）**：`dsh.kind`（`library`/`preset`）· `dsh.ui=false` + `dsh.uiReason`（截图门禁豁免）· `dsh.presetReason` · `dsh.client.externalDegraded`。官方 `DshManifest` 只有 `manifestVersion`/`bundle`/`profile`/`client`。

## 四、容易被误导：文档/skill 提到但代码零使用的 API

改代码前若在这些名字上打转，先看这行——**当前仓库没有调用者**：

- `inputMachine` / `facade` 的 insert/consume/remove/subscribe —— **已从宿主移除**（本机 0.1.5-rc.1 与官方参考源双树均零命中），本仓库 0 调用；skill `plugin-runtime-debug` 曾以它为示例，已按此订正。
- **`ctx.config`** —— 全仓 6 处出现**全在注释里**（现场统计 `grep -rn 'ctx.config' plugins/*/src`），真实调用 0；配置入口是 `apply(ctx, config)` 第二实参，且客户端根本访问不到它（改动时别照注释写代码）。
- **`ctx.get('slots', false)` 是成立且在用的写法**：client 插件机会性取 `slots` 服务（src 14 处，现场统计 `grep -rn "ctx.get('slots'" plugins/*/src`；席位注册本身仍由 `ctx.slots.inject` 等待就绪）。**必须显式传 `false`**——`strict` 默认只返回「提供方 fiber 当前 active」的实现，首屏未 active 时静默 undefined，页签就不出现。
- `settings.plugin.item` / `ctx.settingsScope` / `ctx.settings.installSection` —— **当前宿主不存在这三者**（参考源全树零命中），本仓库 0 调用；本仓库设置页走 `settings.plugins.tab` + localStorage，host 半零使用。`ctx.settings` 当前只提供 `describe()` / `openSettingsDocument()` / `write`；宿主真实的设置席位是 `settings.section`(list/root，必填 `id`) 与 `settings.plugins.tab`(list/root，必填 `id`)，插件页细粒度席位是 `plugins.item`(list/root，必填 `id`) 与 `plugins.detail.*`(均 list/root)——席位与必填字段查宿主 `slot-catalog.ts`（见[索引](索引.md) 第二节）。

## 五、官方文档 vs 本仓库代码冲突时怎么判

0. **先取证，不许猜**：判「这个 API 到底存不存在 / 什么语义」用**官方参考源的本地图谱**（用法见[索引](索引.md) 第二节）——`search_graph` 找定义点、`trace_path` 看调用链、`grep` 兜底。**四个通道全空**（清单见[索引](索引.md) 第二节）时，它才不是宿主能力——第一节能力表曾登记过一个四通道全空的"服务"（聚合端点的清单来源），实测确认不存在后已改用 `ctx.pluginInventory`（见 3.2）。
1. **语义冲突** → 以**本机运行包**为准：`~/.npm-global/lib/node_modules/@deepseek-ai/*`（读 `*.d.ts` 与 `lib/`）。
2. **用法冲突** → 以**本仓库现有插件**为准（找一个在用的照抄，别照官方示例重写）。
3. 官方 docs 反映 `master`（当前基线用 `node scripts/harness-ref.mjs --status` 查，本页不写死版本号），本机可能落后——**本机优先**。
4. **实例（不是对错，是用途不同）**：设置页槽位——官方设置页席位是 `settings.section` 与 `settings.plugins.tab`，插件页细粒度席位是 `plugins.item` 与 `plugins.detail.*`；本仓库用列表页 `settings.plugins.tab` + localStorage。席位与必填字段一律查宿主 `slot-catalog.ts`（见[索引](索引.md) 第二节）。

## 七、这份文档怎么维护（改了代码之后）

第一节的能力清单是**从 `plugins/*/src` 取证**得出的派生内容（不是凭记忆写的观点），由门禁 `doc-api`（`scripts/check-doc-api-drift.mjs`）双向守护：**文档提到代码里不存在的 API**、**代码在用而文档没登记**，两者都会变红——别手工凭记忆改。

| 代码改了什么            | 门禁会报什么                    | 你要做什么                                                                   |
| ----------------------- | ------------------------------- | ---------------------------------------------------------------------------- |
| 调用新宿主 API / 新插件 | 报「代码在用的 X 未登记」       | 在第一节表格加一行（能力 / 用途 / 范例 / 官方页）                            |
| 移除或替换某个 API      | 报「文档声明 X 但代码里找不到」 | 改该行；确属"有意标注为不存在"则登记 `INTENTIONALLY_ABSENT` 并在文档写明理由 |
| 发现新陷阱 / 新自研契约 | 不报（事实类）                  | 人工写入第三节；踩坑类事实归 `docs/踩坑/`                                    |

```bash
npm run check:doc-api                                          # 只跑本门禁
npm run verify                                                 # 全量（CI 等价）
npx vitest run --config scripts/test/vitest.config.mjs check-doc-api   # 门禁自测
```

本页只放「从代码派生」的清单与官方页映射；踩坑类事实归 [docs/踩坑/](../踩坑/README.md)。
