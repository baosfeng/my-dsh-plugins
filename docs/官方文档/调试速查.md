# 插件调试排障速查

> ⚠️ **何时阅读：** 插件行为异常、且不想靠猜时。先按「一」钉住四个事实，再到「二」按症状取根因方向。
>
> **本页只留本仓库实战内容**（定位方法与症状映射）。官方原文——事故复盘、防御性写法、测试机制、事件归属——直接查参考源，入口与命令见[索引](索引.md) 第三节：转述副本会漂移，故不在此维护。

## 一、定位起手式：四个事实，缺一个就别往下猜

**0. 先钉住身份：哪个进程、哪个 origin、哪个源码树。** 官方事故复盘里最贵的一次错误，就是验收了另一个服务器而非当前 GUI。

- 当前 GUI 的规范 URL 由宿主发布，不要猜端口：shell 变量 `$DSH_WEB_URL`（与 `app:web-surface` 提示词区段同源）。
- 组合树与层序：`dsh --profile web --dump-config`（profile 组合包 → `cordis.patch.yml` → home → `--patch` overlay）；装插件只走 `dsh plugin --profile web add <包>`。
- 要改宿主行为/替换能力实现时，先定 seam 三角色（Service Definition / Provider / Consumer）再动手，别按名字猜服务。
- **契约有疑问就回源码**：判「这个服务/事件到底存不存在、定义在哪个包、serial 还是 parallel」用本地参考源图谱（命令见[索引](索引.md) 第二节）——官方 docs 只列事件名，不给分发契约；**四个通道全空才判「不是宿主能力」**（别只看 `--query`，它会误杀真实服务；本仓库 `ctx.bundler` 实测四通道全空，静默降级为空列表）。

**1. 插件是否加载。** `dsh web` **先监听端口、后加载插件树**——端口能回 HTTP 不代表插件树活着。

- 启动日志 grep 致命串：`plugin tree failed to load`、`entry did not activate`、`without inject`、`cannot get property`、`in inactive context`、`missed the module table`、`window.__DSH_BOOT__ is missing or not an object`。
- 真实 Loader 路径冒烟：参考源 `packages/test-support/loader-smoke`（从 bin + `cordis.yml` 起隔离 cwd）。

**2. 进程是否活着。** 「端口有响应」≠「应用就绪」：裸 Vite 同样返回 200。

- 就绪需三条同时成立：端口有 HTTP 响应 + 日志出现正向就绪行 + 进程仍存活。
- 长驻进程一律用受管后台任务，**不要** shell `&`：任务身份、完成通知、结果收集与清理都会失效。

**3. 前端是否拿到模块。** 浏览器 console 是唯一现场。

- `window.__DSH_BOOT__` 缺失或非对象 ⇒ 页面没拿到宿主注入的启动图（白屏常态）；它只由完整宿主注入。
- 模块路由 `/plugins/??<包A>/client.js,<包B>/client.js&rev=<rev>`：404 = 未知/被改的资源列表、缺 revision 或**陈旧 revision**；405 = 方法不对。
- 插件进表条件：`package.json` 声明 `dsh.client`（`platform: 'web'`）且有 `exports["./client"]` 构建产物。

**4. 事件是否发出。** 先定事件域，再查对应载体。

- 三个事件域选一个：持久**会话事件**（`session/event`，落日志）/ 实时 **`agent/*`**（携带活跃 Agent）/ **能力事件**（`fs/*`、`tools/*`）。waterfall 监听器不调 `next()` 就断链；scoped 事件只投给 scope 匹配者。
- 持久事实查会话日志：`$DSH_HOME/sessions/<cwd 转义目录>/<sessionId>/session.jsonl[.zstd]`（v1 起为 `session.vN.jsonl`）。
