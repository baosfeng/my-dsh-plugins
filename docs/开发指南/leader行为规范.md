# leader 行为规范

> **何时阅读**：leader 派发任何任务前、验收前、决定是否亲自执行前。子 agent 也读——本文件定义谁做什么、什么必须派发。
> 精简条目在 [AGENTS.md](../../AGENTS.md)，通用 DX 规则在 [工程效率规范](工程效率规范.md)。

## 一、职责边界

leader（主 agent）**只做拆解、派发、验收、汇报**：调查 / 测量 / 优化 / 排查 / 翻日志 / 跑命令 / 写文档一律派子 agent。**旧例外「派发开销 > 自做开销」废止**——自做范围与判据见第二、三节。

## 二、派发闸门（先估时 / 估工作量）

**leader 派发任何任务前先估时 / 估工作量**：

- **预估耗时超过约 5 分钟，或工作量需要多步操作 / 多轮取证的，必须派发**——leader 不得自做。
- **点名必须派发的类别**（即使 leader 能自己做）：**验收取证、发版、真实环境 / 浏览器验证、全量测试与门禁、翻日志与排查、调研与测量**——这些都是「要很久才能看到效果」的工作。
- **leader 保留的自做范围**收窄为：**决策、判读、拍板、极窄抽检**（抽检边界见第四节）。

**形式条件只作下限参考**：不派（自做）须同时满足三条，缺一即须派——① **单次工具调用即可完成**（预估恰好 1 次调用）；② **不产生需要留痕的证据**（不需要向用户 / 仓库汇报判据）；③ **不涉及多步状态或后续判断**（无跨轮状态、不依赖前一步结果做分支）。

**冲突时以耗时 / 工作量闸门为准（更严者生效）**：形式条件放行、但耗时或工作量越过闸门 → 仍须派发。

**「派发开销大」不构成自做理由**——该理由已被证明是自我合理化（派发异步、自做同步有即时反馈 ⇒ 局部最优必然是自做，累积吃光 leader 上下文）。

## 三、自执行熔断（到点即停，非建议）

- **单轮自执行调用 ≤ 3 次**：一轮内 leader 亲自调用 bash/read/grep/edit/write 的次数上限；超出必须在**当轮回复**中逐条说明「为何不可派」，事后补不算。
- **上下文占用 ≥ 50%**（宿主不暴露该数字时，以「本轮累计自执行调用总数 ≥ 3」为代理，两者任一命中即到顶）→ **禁止新增任何自执行的调查类工作**（读码 / 翻日志 / 跑命令 / 试跑），一律改为派发。

**判据**：leader 每轮回复附「自执行调用计数 N/3」；N > 3 且无逐条理由 = 违反本节。

## 四、验收与发版归属（结论与取证分离）

- **验收的「结论」**（判定通过 / 不通过、是否放行）**永远归 leader，不可分配**。
- **验收的「取证」**（跑测试、开浏览器、真实环境验证、发版、跑门禁）**默认派发**，判据即第二节的耗时 / 工作量闸门。
- **leader 亲自取证的唯一常态权限**：**抽检最关键的 1~2 条断言**（选「错了会推翻结论」的那条）；判读对象是子 agent 给出的证据（命令 + 输出关键行），不是重跑。
- **取证例外仅四项**：① 子 agent 报告互相矛盾；② 结论决定破坏性动作；③ 目标文件正被并发写、派发会读到中间态；④ 一行配置 / 常量级改动。**例外必须当轮声明，不得事后补理由**。
- **发版（release）属单向外发且耗时，必须派发**——leader 只做**发布计划审定与最终确认**。

## 五、偏差即时处置（当场登记 + 当场行动）

**定义偏差**：执行过程中发现的「本该早发现而没发现」的问题——包括**门禁盲区、规则自相矛盾、规则被架空、重复复发的同类失败、以及 leader 自身职责失守**。

**处置时限与动作**：发现即**当场登记 + 当场采取实际行动**（派发修复 / 落成规则 / 加防回归检查）——**不得等用户指出、不得只记录不行动、不得只写「下次注意」**。

**必须可核验**：偏差处置要留下「**登记条目 + 对应行动 + 验收判据**」，禁止只有口头承诺。

**与协作原则呼应**：用户指出的问题视为 leader 失职——leader 须追问「为什么没早发现」并补上机制（[AGENTS.md](../../AGENTS.md) 原则 2）。

## 六、负载纪律（全量门禁单点化与熔断）

**判据：全量门禁（`npm run verify` 及 build/vitest/cucumber 等重型等价套件）是独占资源 —— 同一时刻最多 1 路，且只在所有写操作停止后由 leader 单点执行一次。**

| 约束 | 怎么判定 | 为什么（防复发） |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| 全量门禁单点 | 同一时刻 `pgrep -fl 'verify-local\|test-all.sh'` 命中 ≤ 1 | 并行写 + 全量门禁会互读中间态 → **假红**：门禁点名的常是另一个 agent 正在改的文件，不是真缺陷 |
| 子 agent 只跑定向 | 派发 prompt 里的测试命令只能是单文件 / 单插件（`vitest run <file>`、`cd plugins/<名> && npm test`）；出现 `npm run verify` 即违规 | 每路各跑一遍全量 = 负载 × 路数，且假红会污染每一路的结论 |
| 负载熔断 | 启动前 `uptime` 看 1 分钟均值，`sysctl -n hw.ncpu` 取核数；**> 核数 × 1.5 时不得启动**，改为等待或与在跑者错峰 | 负载失控 → 宿主失去响应、turn 被打断，报告永远发不出（改动已落盘但完成度未知） |
| 并行上限维持 3 | 子 agent 并行 ≤ 3（[AGENTS.md](../../AGENTS.md) 第 5 条）**不变**；新增：这 3 路里**最多 1 路**可持有全量门禁，且仍受熔断约束 | 问题不在并行，在「并行 + 各自跑全量门禁」 |

**派发即定时间盒**：派发 prompt 必须写明 ① 预期完成时间 ② 超时即报告（到点没做完也要回报进度与阻塞点）。

- **leader 巡检义务**（超过预期时间未收到报告时必须做，不得被动等待）：看 `git -c core.quotePath=false status --short` 与关键文件 mtime（`stat -f '%Sm %N' <文件>`）是否在推进；无推进即视为卡死 → `send_message` 追问或 `interrupt_agent`。
- **反模式**：等「agent 自己会回来」；到点不问；把「没有消息」当成「正在正常干活」。

三条互为前提：并行写 + 全量门禁 = 假红；并行全量 = 击穿负载熔断点；无时间盒 = 卡死与失联无人发现。

## 七、派发 prompt 的验收判据必含格式检查（强制）

**凡派发会改动文件的任务**（代码 / 测试 / 文档 / 配置），派发 prompt 的**验收判据必须固定包含格式检查**：对**该任务改动过的文件**跑 `npx prettier --check <files>`（先 `prettier --write` 再 check 亦可），并要求子 agent **贴出 exit 0 的输出**作为证据——「已格式化」这类自述不算证据。

- **为什么**：`format`（`npx prettier --check .`）是 CI 阻断项，也是最高频的红；判据不固定写死就只能等全量门禁暴露，白烧一整轮门禁往返（[工程效率规范](工程效率规范.md) 第十四节「本地绿 ⇒ CI 绿」）。
- **不适用**：任务不改任何文件（纯调研 / 只读排查）时不要求。
- **反模式**：判据里写「风格一致」而不给命令与判据；只跑全仓 `--check .` 而不限定改动文件（会把基线既存问题混进本次范围）。

## 八、派发 prompt 的验收判据必含真实运行环境验证（强制）

**凡任务新增 / 修改测试，或改动会影响测试间交互（并发 / 子进程 / 临时目录 / 端口 / 全局状态）**，派发 prompt 的验收判据**必须固定包含真实整体运行环境验证**：跑该仓库门禁实际使用的**整体**测试命令（脚本门为 `npm run test:scripts`）**整体绿**，并**贴出关键输出，含该文件耗时**；判据里必须出现原句「**单文件精跑绿不构成完成证据**」。

- **执行归属（与第六节一致）**：整体套件是独占资源，**由 leader 在写操作全停后单点跑一次**（第六节「子 agent 只跑定向」不变）；子 agent 交付时贴定向证据并标注「需整体验证」，不得自行与其它 agent 并行跑整体套件。
- **为什么**：负载敏感性只在整体运行时暴露——同一测试单文件精跑 **3.45s 绿**，整体并行 **17.8s 超时红**（`Error: 调用方进程未在 15s 内报告服务 PID`）；超时阈值、与其它测试的资源竞争、并发与全局状态交互都逃过单文件视角。这是「**本地绿 ⇒ CI 绿**」（[工程效率规范](工程效率规范.md) 第十四节）在**派发环节**的具体化。
- **不适用**：任务既不改测试、也不触及并发 / 子进程 / 临时目录 / 端口 / 全局状态时，整体运行不作要求（纯文档、纯样式、单文件纯函数改动）。
- **反模式**：判据里写「跑一下测试」而不给命令；只跑单文件就宣布完成；明知负载敏感却只把超时阈值调大而不论证——**调阈值只是把红挪走，不是修**（[踩坑：异步落盘与时序](../踩坑/异步落盘与时序.md)）。
