# 依赖升级矩阵

> ⚠️ **何时阅读：** 想升级某个依赖 / 判断「这个包该不该升」/ 新增插件后确认自动更新是否覆盖 / 收到 dependabot PR 想知道它属于哪一档。

## 一、怎么用

| 命令                          | 用途                                              |
| ----------------------------- | ------------------------------------------------- |
| `npm run deps:matrix`         | 人类可读报告：按 A/B/C/D 分档分组，含声明漂移小节 |
| `npm run deps:matrix:md`      | markdown 表格（贴 PR / 存档）                     |
| `npm run deps:matrix:offline` | 不联网，只用缓存（缺缓存项标 `?`）                |

直接调 `scripts/deps-matrix.mjs` 可加 `--json` / `--refresh` / `--registry=URL` / `--out=FILE`。结论与数据都**一条命令复现**，不要靠记忆。

**设计约束（刻意选的）**：

- **只读**：不写任何 `package.json` / lock，唯一写动作是缓存文件（已 gitignore，`--offline` 时连它也不写）。
- **不联网也能用**：registry 查不到只把该项降到 `?` 档并写明原因，不让整个盘点挂掉。
- **输出稳定**：按包名 ASCII 升序、按档分组、行内不含时间戳，两次运行可直接 diff。
- **默认官方 registry**：镜像的 `latest` 标签与上游存在偏差。
- **`@types/node` 按分支比较**：它的 npm `latest` 标签刻意停在旧 LTS 分支，照抄 `latest` 会得出「已最新」的反向结论。

## 二、分档口径

| 档     | 含义                                                 | 处置                                 |
| ------ | ---------------------------------------------------- | ------------------------------------ |
| **A**  | 可直接升（patch / minor，风险低）                    | 直接升，顺带修声明漂移               |
| **B**  | 需验证后升（跨大版本 / 预发布 / 宿主或仓库内包协同） | 先验证再升；宿主随包只能跟随宿主升级 |
| **C**  | 有硬阻塞                                             | 先解阻塞再谈升级                     |
| **D**  | 破坏性，须先决策                                     | **必须用户确认**（公开 API 变更）    |
| **OK** | 已是最新                                             | 不动                                 |

## 三、已定决策（勿重复论证）

- **宿主随包（`cordis`、`@deepseek-ai/dsh-*`）：改声明不改变运行时实际版本**，只能跟随宿主升级（走 `skills/plugin-upgrade/SKILL.md` + `skills/dsh-upgrade-audit/SKILL.md` 的流程）。矩阵里显示 `[ahead]` 多半是 npm `latest` 标签语义问题，不是真落后。
- **仓库内包（`dsh-shared` / `dsh-md-render`）：声明漂移是正常形态**，升级需协同发版，改动要连带发版、不能只改声明。
- **jscpd 锁 `^5.2.0`**：5.x 为 Rust 自包含二进制，需 GLIBC ≥ 2.33。**回退方式**：`npm i -D jscpd@^4.3.0` 一行回滚（4.x 与 5.x 的 `.jscpd.json` 完全兼容）。背景见 [踩坑目录](../踩坑/README.md)「jscpd 门禁报 GLIBC not found」。
- **react 保持双版本声明 `^18.2.0 || ^19.3.0`**（收益 < 成本）：运行时版本由宿主决定，插件收窄声明**不改变任何渲染行为**；插件 client 代码 100% 兼容 18 与 19（见 [React 19 兼容性评估](React19兼容性评估.md)），双声明是事实描述而非技术债；收窄为 19-only 还会与上游 sidebar 的 `react: ^18.2.0` 声明冲突，并需 14 个插件整批发版。若要放弃 React 18 用户，顺序是：先与上游对齐 → 改插件 peer 声明 → 整批发版 → 更新评估文档。

## 四、防漂移：dependabot 覆盖

多包布局（根 + 19 个 `plugins/<name>`）下，只配 `directory: '/'` 会漏掉全部插件的 devDeps。方案：`npm` + `directory: '/'`（根工具链）、`npm` + `directories: ['/plugins/*']`（19 个插件目录，**新增插件自动纳入**）、`github-actions` + `directory: '/'`。

- **分组策略（防 PR 风暴）**：每个目录内按 `update-types` 分两组——minor+patch 合并成一个 PR，major 单独一个 PR（跨大版本本就该逐个读 CHANGELOG）；再用 `open-pull-requests-limit` 封顶（插件 3 / 根 5）。
- **`allow: dependency-type=development`**：自动更新只覆盖 devDependencies。插件的 `peerDependencies`（cordis / react / dsh-shared / dsh-md-render）是**公开兼容声明**，收紧 react 双支持、跳 cordis rc 这类动作属破坏性变更（D 档），必须人工决策；安全更新不受 `allow` 限制，仍会照常开 PR。
- 暂不迁 Renovate：它对 monorepo 更强（自动发现全部 `package.json`、跨目录合并 PR、dependencyDashboard），但需要 GitHub App / 自托管 runner。**迁移触发条件**：插件目录数 > 40、或出现「跨目录必须合并成一个 PR」的刚需、或需要按依赖类型精细排期。

## 五、已知陷阱

- **CI 从不安装插件级 devDeps**（只跑根 `npm ci`），插件的 `npx tsc` 一律向上解析到根 node_modules 的 TS。所以插件 `package.json` 里过期的 `typescript` / `@types/node` 声明是**从未生效的死声明**，但会误导 clone 后 `cd plugins/<name> && npm install` 的人——发现漂移要按 A 档对齐，并如实说明这不是修 CI。
- 本地实装验证才是证据：改声明后跑 `npm install`（把插件对主工作区的软链换成 fork 内真实副本）+ `npx tsc --noEmit -p tsconfig.json` 与 `-p tsconfig.client.json` + `npm test`。
- lock 的 registry 可能混用（官方 + 镜像），两个源 CI 均可访问，属正常现状。
