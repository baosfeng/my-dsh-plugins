# 依赖升级矩阵（issue #184）

> **何时读：** 想升级某个依赖 / 判断「这个包该不该升」/ 新增插件后确认自动更新是否覆盖 / 收到 dependabot PR 想知道它属于哪一档。
> 结论与数据都可以**一条命令复现**，不要靠记忆：`npm run deps:matrix`。

## 一、怎么用（先把现状变成可复现的矩阵）

| 命令                          | 用途                                              |
| ----------------------------- | ------------------------------------------------- |
| `npm run deps:matrix`         | 人类可读报告：按 A/B/C/D 分档分组，含声明漂移小节 |
| `npm run deps:matrix:md`      | markdown 表格（贴 PR / 存档）                     |
| `npm run deps:matrix:offline` | 不联网，只用缓存（缺缓存项标 `?`）                |

直接调脚本可加参数：`node scripts/deps-matrix.mjs --json`、`--refresh`、`--registry=URL`、`--out=FILE`。

**设计约束（都是刻意选的）**：

- **只读**：不写任何 `package.json` / lock，唯一写动作是缓存文件 `.deps-matrix-cache.json`（已 gitignore，`--offline` 时连它也不写）。
- **不联网也能用**：registry 查不到只把该项降到 `?` 档并写明原因，不让整个盘点挂掉 —— 离线/镜像不可达时「当前版本」部分照常输出。
- **输出稳定**：按包名 ASCII 升序、按档分组、行内不含时间戳，两次运行可直接 diff（升级前后对比靠它）。
- **默认官方 registry**：镜像的 `latest` 标签与上游存在偏差，结论要能对得上 npm 官方。
- **`@types/node` 按分支比较**：它的 npm `latest` 标签刻意停在旧 LTS 分支（实测 `latest=22.20.2`，而当前分支最新是 `26.5.1`），照抄 `latest` 会得出「已最新」的反向结论。

## 二、分档结论（2026-09-12 现场盘点）

矩阵覆盖 **20 个 package.json**（根 + 19 个插件）× **32 个外部依赖**，含 `dependencies` / `devDependencies` / `peerDependencies` / `overrides` 四类声明。

| 档     | 含义                                                 | 本次盘点结果                              |
| ------ | ---------------------------------------------------- | ----------------------------------------- |
| **A**  | 可直接升（patch / minor，风险低）                    | 落地前 7 项 → **落地后 0 项**             |
| **B**  | 需验证后升（跨大版本 / 预发布 / 宿主或仓库内包协同） | 6 项（全部是宿主随包与仓库内包）          |
| **C**  | 有硬阻塞（先解阻塞再谈升级）                         | 1 项（jscpd）→ **已解锁升 5.x**           |
| **D**  | 破坏性，须先决策                                     | 2 项（react / react-dom，**待用户确认**） |
| **OK** | 已是最新                                             | 24 项                                     |

### B 档（需验证 / 协同，本批不动）

- **`cordis` `^4.0.0-rc.8` → 4.0.0-rc.10**：由 DSH 宿主提供，插件改声明不改变运行时实际版本，只能跟随宿主升级（走 `skills/plugin-upgrade` + `skills/dsh-upgrade-audit` 的流程）。
- **`@deepseek-ai/dsh-*` `^0.1.1-rc.1`**：同上（宿主随包）。矩阵里显示 `[ahead]` 是因为这些包的 npm `latest` 标签停在更旧的 `0.0.1-rc.1`，属标签语义问题，不是真落后。
- **`dsh-shared` / `dsh-md-render`**：仓库内包，升级需协同发版；矩阵里两者都有「声明漂移」（根用 `file:` 而插件用 `^0.1.x`、插件间 peer 版本不一致），**这是仓库内包的正常形态**，改动要连带发版，不能只改声明。
- **`dsh-better-sidebar` `>=0.14.0`（实装 0.18.0）→ 0.19.1**：原判为 A 档，现场验证**降级为 B**：0.19.1 新增了对宿主包的 peer 要求 `@deepseek-ai/dsh-*@^0.1.5-rc.1`，本仓库当前宿主解析结果是 `0.1.2-rc.1` 一系，`npm install` 直接 `ERESOLVE`（证据：`Conflicting peer dependency: @deepseek-ai/dsh-llm@0.1.5-rc.2`）。**须与 DSH 宿主版本联动升级**，不能单独升。根声明保留 `>=0.14.0`（让宿主决定），插件侧声明同步收紧另议。

## 三、已落地：dsh-my-memory devDeps 漂移修正

**问题**：`plugins/dsh-my-memory/package.json` 的 devDeps 是 `typescript@^5.0.0` + `@types/node@^20.0.0`，而其余 6 个带 devDeps 的插件均为 `typescript@^7.0.2` + `@types/node@^26.4.0` —— **分别落后 2 与 6 个大版本**，且实装 `@types/node@20.19.43`。

**修正**：`typescript ^5.0.0 → ^7.0.2`、`@types/node ^20.0.0 → ^26.5.1`；同时把另外 6 个插件的 `@types/node` 从 `^26.4.0` 对齐到 `^26.5.1`（A 档）。修完后矩阵的「声明漂移」从 4 项降到 2 项（剩下的两项是仓库内包，属预期）。

**验证证据**（本地实装，非"应该没问题"）：

- `plugins/dsh-my-memory/node_modules` 实装 `typescript 7.0.2` + `@types/node 26.5.1`（先把它对主工作区的软链换成 fork 内真实副本，才做的 `npm install`）；
- `npx tsc --noEmit -p tsconfig.json`（server）与 `-p tsconfig.client.json`（client）**均无输出、退出 0**；
- `npm test`：vitest **195 passed**（覆盖率 96.09% 行 / 85.89% 分支）+ cucumber **26 scenarios / 156 steps 全过**。

> ⚠️ **一个容易误解的事实**：CI 只跑根 `npm ci`，**从不安装插件级 devDeps**，插件的 `npx tsc` 一直向上解析到根 node_modules 的 TS 7 —— 也就是说「插件在 TS 7 下能不能过」CI 早就在验证，而插件 `package.json` 里的 `typescript@^5` 只是**从未生效的死声明**，会误导 clone 后 `cd plugins/<name> && npm install` 的人。本次把它对齐，是消除语义漂移，不是修复 CI。

## 四、jscpd 决策记录：锁 4.x 的阻塞已解除 → 升 5.2.0

**原阻塞**（`docs/踩坑/jscpd原生二进制对glibc基线敏感.md`）：jscpd 5.x 是 Rust 自包含二进制，要求 GLIBC ≥ 2.33；当时跑在 **云效 alinux3 容器（glibc 2.32）** 上，loader 直接拒绝加载，门禁恒红且没有任何 clone 清单输出，于是刻意锁 `4.3.0`（纯 JS）。该踩坑文档同时写明了**回退条件**：「若将来 CI 的 glibc 基线 ≥ 2.34（ubuntu-22.04+ runner 等），可升回 jscpd@5.x」。

**本次复核（阻塞是否仍存在）**：

1. 仓库已「回滚到 GitHub 单一主线、移除全部云效配置」——`grep -ril 'yunxiao|云效|alinux' `（排除 node_modules/.git）**零命中**；
2. `.github/workflows/*.yml` 全部 `runs-on: ubuntu-latest`，无自建/容器化 runner；
3. GitHub 托管 `ubuntu-latest` 现为 Ubuntu 24.04（glibc 2.39 ≥ 2.34）→ **回退条件成立，阻塞不再存在**。

**本地验证（macOS arm64，jscpd 5.2.0）**：`.jscpd.json` 的 `format` 白名单与 `ignore` 全部生效，跑出 3 clones / 0.09%（阈值 5%）→ **exit 0**；耗时 **41ms**（4.3.0 同样扫描为 4.4s，约 100 倍）。附带差异：5.x 检出 3 个 clone 而 4.x 报 1 个（引擎/去重差异），都远低于阈值，**门禁结论一致**。

**决策**：升 `jscpd@^5.2.0`。**未验证项**：Linux 侧二进制可加载性只有 CI runner 能给证据 —— 本次 PR 的「Duplicate code check (jscpd)」步骤即闭环验证。**回退方式**：`npm i -D jscpd@^4.3.0` 一行回滚（4.x 的配置完全兼容，不需要改 `.jscpd.json`）。

## 五、react 双版本支持（D 档）：分析与建议 —— **待用户决策，本批不动**

**现状**：14 个插件的 peer 声明是 `react: ^18.2.0 || ^19.2.0`（`dsh-mermaid-render` 另有 `react-dom` 同款双范围）。npm 上 `react@19.3.0` 已发布，仓库实装 19.2.8。

**收益**：声明更贴合事实（DSH 宿主运行时是 React 19）。

**风险 / 反对理由**：

1. **运行时版本由宿主决定，插件收窄声明不改变任何渲染行为** —— 收窄只缩小「可被安装」的范围，换不到任何功能；
2. **与上游 `dsh-better-sidebar@0.19.1` 的声明冲突**：它自己声明 `react: ^18.2.0`（不含 19），我们若收紧为 19-only，install 时会出现 peer 冲突观感，得先推动上游改；
3. issue #49 的评估结论是**插件 client 代码 100% 兼容 React 18 与 19**（见 `docs/开发指南/React19兼容性评估.md`），双声明是事实描述而非技术债；
4. **成本是破坏性的**：14 个插件声明 + 19 个包需要整批发版（公开兼容声明变更），还要同步改 README 与评估文档。

**建议**：**保持双版本支持不改**（收益 < 成本）。若用户明确要放弃 React 18 用户，执行顺序应为：先与 sidebar 上游对齐 → 改 14 个插件 peer 声明 → 整批发 patch/minor 并发版 → 更新 React 评估文档。此项**必须用户确认后**才能动（公开 API 变更）。

## 六、防漂移：依赖自动更新已覆盖 19 个插件目录

**根因**：`.github/dependabot.yml` 原配置只有 `directory: '/' `，而本仓库是「根 + 19 个 `plugins/<name>`」的多包布局 → 19 个插件的 devDeps **全在覆盖之外**，dsh-my-memory 的 TS 5 / @types/node 20 漂移就是这么攒出来的。

**方案**（`.github/dependabot.yml`）：

| 条目                                  | 覆盖                                  | 分组                                                  |
| ------------------------------------- | ------------------------------------- | ----------------------------------------------------- |
| `npm` + `directory: '/'`              | 根工具链                              | `root-toolchain-minor-patch` / `root-toolchain-major` |
| `npm` + `directories: ['/plugins/*']` | **19 个插件目录**（新增插件自动纳入） | `plugin-devdeps-minor-patch` / `plugin-devdeps-major` |
| `github-actions` + `directory: '/'`   | workflow action 版本（原有）          | —                                                     |

- **覆盖方式**：`directories` + 通配符 `/plugins/*`。通配符能力来自 GitHub Changelog 2024-06-25「Simplified dependabot.yml configuration with multi-directory key (directories) and wildcard / glob (*) support」。本地按同一 glob 语义核对：**19/19 覆盖，无遗漏**。
- **分组策略（防 PR 风暴）**：每个目录内按 `update-types` 分两组 —— minor+patch 合并成一个 PR（低风险批量过），major 单独一个 PR（跨大版本本就该逐个读 CHANGELOG）。再加 `open-pull-requests-limit`（插件 3 / 根 5）封顶总量。
- **`allow: dependency-type=development`（关键安全设计）**：自动更新**只覆盖 devDependencies**。插件的 `peerDependencies`（cordis / react / dsh-shared / dsh-md-render）是**公开兼容声明**，收紧 react 双支持、跳 cordis rc 这类动作属破坏性变更（D 档），必须人工决策；`dependencies` 同理（`dsh-better-sidebar` 实测直接升会 ERESOLVE，见第二节）。安全更新（security updates）不受 `allow` 限制，仍会照常开 PR。
- **校验**：YAML 解析通过 + 官方 SchemaStore `dependabot-2.0.json` schema **PASS**（本地用 ajv 校验）。

**Renovate 评估（建议暂不迁）**：Renovate 对 monorepo 更强 —— 自动发现全部 `package.json`（不必列目录或写 glob）、`packageRules` 跨目录统一规则、**跨目录合并成一个 PR**（dependabot 的 group 只能在单个目录内合并）、dependencyDashboard、排期可控。代价是需要 GitHub App / 自托管 runner，而 dependabot 是 GitHub 原生、零维护、安全更新与 Actions 生态开箱即用。**当前 19 个插件、每个插件只有 2 个 devDeps 的规模，dependabot + groups 已够用**。迁移触发条件：插件目录数 > 40、或出现「跨目录必须合并成一个 PR」的刚需、或需要按依赖类型精细排期。

## 七、未验证项与风险（诚实记录）

1. **jscpd 5.x 的 Linux 二进制**只有 CI runner 能验证（本地证据仅 macOS arm64）→ 本 PR 的 CI 即闭环；失败则一行回退到 4.3.0。
2. **dependabot 的实际行为**要等下一个周一 09:00 的周期才会真实运行（无法本地触发）；「19/19 覆盖」是静态核对结果。
3. **`dsh-better-sidebar` 升级被宿主 peer 拦住**，需与 DSH 宿主版本联动（属 `plugin-upgrade` / `dsh-upgrade-audit` 那类工作）。
4. **lock 的 registry 混用**：本次 `npm install` 走官方 registry，新增/升级条目的 `resolved` 指向 `registry.npmjs.org`，其余条目仍是 `registry.npmmirror.com`（与 main 现状一致，两个源 CI 均可访问）。
5. **插件 devDeps 在 CI 中从不安装**（见第三节的说明），所以这些声明变更的证据来自本地实装验证 + `typecheck-all`。
