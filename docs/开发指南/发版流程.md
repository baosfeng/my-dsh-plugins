# 发版与打包流程

> 目标：**一次发版 = 版本 bump + CHANGELOG + GitHub Release + npm 发布全部自动完成**。
> 本文档是流程说明；可自动化部分已沉淀到 `scripts/release.mjs` 与 `.github/workflows/`（见下文"自动化覆盖"），文档只记录必须人工判断的规则与踩坑。

## 发版方式（二选一）

### 方式 A：GitHub Actions 自动发版（推荐）

1. 仓库 **Actions** → **Release (auto)** → **Run workflow**
2. 填写 `plugins`（一个或多个插件目录名，多个用**逗号或空格**分隔，如 `dsh-md-render,dsh-my-guard`）+ 选择 `bump`（下拉**单选**：patch / minor / major）
   - `plugins` 是**文本框**（`type: string`），不是下拉：GitHub Actions 的 `choice` 只渲染单选下拉、原生不支持 `multiple`，要一次发多个只能用文本分隔（issue #204）
   - 输入先过白名单校验（允许值 = 仓库 `plugins/` 目录，运行时读取，不硬编码清单）：写错/改过名的插件名直接 fail-fast 并列出全部允许值，不会带着错名字发版
3. 自动完成：
   - `release.mjs --bump`：版本 +1、从 `git log <prev-tag>..HEAD` 生成 CHANGELOG 段、提交
   - 同步根 README 插件表（AGENTS.md 版本行，如存在）
   - 打 tag `<插件>@v<新版本>` 并推送 → 触发 `release.yml`
   - `release.yml`：npm test 门禁 → 创建 GitHub Release（tgz 资产）→ **npm 自动发布**（读仓库 `NPM_TOKEN` secret）
4. 等 Actions 两个 run（Release (auto) + Release）全绿即完成

### 方式 B：本地手动（等价命令）

```bash
node scripts/release.mjs <插件名> --bump patch --push   # bump + CHANGELOG + 同步文档 + tag + push
# 或版本已手动改好时：
node scripts/release.mjs <插件名> --push                # 只校验 + 测试 + 同步文档 + tag
```

> `--bump` 可选 patch | minor | major；`--push` 缺省为 dry-run（只校验不提交）。release.mjs 会跑 npm test（门禁：测试全绿 + 截图引用有效 + 跨插件依赖校验 + 真实环境验证）。

### 批量发版（一次发多个插件）

支持一次发版多个插件，所有插件共享同一个 bump 类型：

#### GitHub Actions 批量发版

1. 仓库 **Actions** → **Release (auto)** → **Run workflow**
2. 在 `plugins` 输入框填多个插件目录名，**逗号或空格分隔**（`dsh-md-render dsh-my-guard` 与 `dsh-md-render,dsh-my-guard` 等价，换行/中文逗号也认），再选 `bump` 类型（下拉单选，所有插件共用）
   - **UI 能力边界**：`plugins` 是文本框（可填多个），`bump` 是单选下拉。GitHub Actions 原生不支持下拉多选（`type: choice` 无 `multiple`），所以批量只能走文本分隔（issue #204）
   - **输入校验**：非法/拼错的插件名 fail-fast——报 `非法插件名: <名字>` 并列出全部允许值（运行时 `ls plugins/`，与目录不可能漂移）；重复名字自动去重
3. 自动完成：
   - 每个插件独立校验门禁（一个失败不影响其他）
   - 所有成功插件一次提交 + 逐个打 tag + 推送
   - 失败报告汇总所有失败插件

#### 本地批量发版

```bash
# 批量发版多个插件（统一 bump 类型）
node scripts/release.mjs dsh-file-activity dsh-my-observability --bump patch --push

# dry-run 模式预览（不提交）
node scripts/release.mjs dsh-file-activity dsh-my-observability --bump patch

# 跳过真实环境验证（需提供理由）
node scripts/release.mjs dsh-file-activity dsh-my-observability --bump patch --push --skip-real-verify --skip-reason "批量回归测试"
```

#### 批量发版特性

- **独立校验**：每个插件独立执行完整门禁（版本检查、依赖校验、测试、截图校验等），一个插件失败不影响其他插件
- **并发执行（issue #246）**：默认 3 个插件同时在跑（`--concurrency N` 覆盖，上界 8；单插件恒为 1）。每个插件内部的门禁也并发（静态门禁跑完 → 1a/3/3c 并发）。**并发只改顺序与耗时，不改判定**：任一插件任一子门禁失败 → 该插件失败 → exit 1
- **统一提交**：所有成功插件的变更一次提交（避免多次 commit 污染 git 历史）
- **tag 流水线（issue #246）**：全部 tag 先创建（含冲突防护，冲突即停、绝不 force）→ **一次推送全部 tag**（一次网络往返）→ **并发**等待全部 Release/npm（原来每推一个 tag 就串行等 ~55s，N 个 = N × 55s）
- **失败报告**：脚本结束时汇总所有失败插件，并标出**失败点（门禁编号）**，方便定位问题
- **幂等重试**：已存在的 tag 会检查是否指向当前 HEAD，避免重复操作；同一 `inspectTagState` 三分支（absent / same-head / conflict）

## 耗时结构与流水线（issue #246：发版速度专项）

发版慢在哪**有实测数字**，每次发版结束脚本都会打印阶段耗时表——不必再猜。

### 单插件全链路实测（门禁全绿，13.4s）

| 阶段                                                | 实测         | 占全链路 |
| --------------------------------------------------- | ------------ | -------- |
| **3c 真实环境验证（#67，隔离实例）**                | **9,804 ms** | **73%**  |
| └ 其中：实例冷启动到 HTTP 200 就绪                  | **8,686 ms** | 65%      |
| └ 其中：停止实例 + 清理临时目录                     | 971 ms       | 7%       |
| └ 其中：配置组合 dump-config + 软链校验             | 84 ms        | 0.6%     |
| 1a npm latest 防降级查询                            | 2,554 ms     | 19%      |
| 3 `npm test`                                        | 845 ms       | 6%       |
| 1b / 1b-pre / 1c / 2 / 3b / 4（静态门禁与文档同步） | 合计 < 50 ms | ~0%      |

> ⚠️ **瓶颈结论：发版链路的耗时几乎全在「隔离实例冷启动」（3c = 73%，其中冷启动 8.7s）。**
> 后续任何人想再优化发版，第一眼就该看这里——不要再去抠 CHANGELOG 生成、文档同步这些 <50ms 的环节。
> 已知可行但**未做**的进一步优化：① 隔离实例预热池（跨发版复用已启动实例）；② 3c 与 pack/CHANGELOG 更深的流水线重叠；③ 一个实例内同时校验多个 addon（需改 `verify-real-profile.mjs`，且会改变「单插件隔离」语义）。均记录在 issue #246。

### 优化前后（同环境背靠背 A/B，同一批插件、同一结论）

| 场景                          | before（串行） | after（流水线）                    |
| ----------------------------- | -------------- | ---------------------------------- |
| 3 插件批量（含 3c）           | 44,636 ms      | **10,921 ms**                      |
| 3 插件批量（同负载 A/B 对照） | 85,109 ms      | **40,511 ms**                      |
| 单插件全链路（门禁全绿）      | 13,422 ms      | **10,044 ms**                      |
| 静态门禁失败快速路径          | 869 ms         | **484 ms**（且**不启动隔离实例**） |

### 观察耗时表时的两个口径

- 并发阶段的耗时**之和大于墙钟合计**，属正常（表格按启动顺序排列，不冒充串行）；
- 每条失败都带**门禁编号**（如 `✗ [1c] …`），汇总里的「失败点」取门禁编号顺序上最早失败的那个——并发不改变「谁先挡住」的判定口径。

## 版本号规则（semver）

- **patch**：修复 / 内部重构（行为不变）——拆分、文档元数据更新等
- **minor**：新功能；`0.x` 阶段的不兼容变更（如**包名改名** → 0.2.0）
- **major**：`>=1.0.0` 的不兼容变更
- 每次发版必须更新 CHANGELOG（`--bump` 自动从 git log 生成，可事后补充详情）
- 若代码内硬编码了版本常量，一并同步；tag 版本必须与 `package.json` 版本一致（workflow 强校验，不一致直接失败）

## 打包内容（npm pack）

- 发布内容 = `package.json` `files` 字段 + 默认项（README/CHANGELOG/LICENSE/package.json）
- 每个插件 `files` 已含：lib、assets（截图）、cordis.patch.yml、README、CHANGELOG、LICENSE
- 发版前门禁（release.mjs 自动校验）：
  - `peerDependencies.cordis` 已声明且 major 与其他插件一致（npm 分发后缺失会导致安装失败）
  - **插件形态豁免（issue #231）**：`dsh.kind=preset` + 非空 `dsh.presetReason` 的 **agent preset 资产包**（如 `dsh-plugin-dev-mode`——`agent.cordis.yml`（预设组合）+ `preset.yml`（模式选择器显示元数据）复制到 `$DSH_HOME/.agent-presets/<id>/`，**不挂 profile、无 `cordis.patch.yml`**）豁免 1b 的 `peerDependencies.cordis` 与 3c 的 profile 组合验证；跨插件依赖 / CHANGELOG / 测试 / 效果图门禁照旧（注入未声明的真实 `dsh-*` import 仍被 1c 拦下）。判据 `scripts/lib/preset-gate.mjs`（不写插件名单；声明必须有真实资产且内容成形，与 `dsh.bundle`/`dsh.client` 互斥；有资产却不声明同样被拦）
  - **跨插件依赖（issue #39 + #72）**：client/server 端 `require('dsh-*')` / `import` 的包必须在 `peerDependencies` 或 `dependencies` 声明（issue #72：扫描范围覆盖 server 端 import，声明检查覆盖 dependencies——dsh-shared 等自家工具库用 dependencies 由 npm 自动安装）；声明的仓库内 dsh-* 依赖必须已发布（npm）且已打 tag（`<目录>@v<版本>`）——**依赖先发版、依赖方后发版**（如 dsh-think-zh-expand 依赖 dsh-md-render，必须先发 dsh-md-render）；npm view 返回 404（从未发布）直接阻断，不再被「已打 tag」兜底放行；**解析边界（issue #203）**：扫描前先做轻量词法扫描剔除注释，注释里的示例 `require('dsh-x')` 不计入依赖，字符串/模板/正则字面量内部同样不解析（`const s = "require('dsh-x')"` 不算依赖），真实 `require` / `import ... from` 仍照常提取，检测面未收紧
  - **真实环境验证（issue #39，强制）**：发版前自动跑 `node scripts/verify-real-profile.mjs --addons plugins/<名> --clean-externals`（真实 DSH 实例 + 配置组合检查 + 日志错误扫描），失败即阻断发版；CI（GitHub Actions）无生产 profile 自动跳过，本地可用 `--skip-real-verify` 显式跳过（仅限无法起真实实例的场景，如批量回归）
    - **崩溃必须 fail-closed（issue #305）**：`dsh web` **先监听端口、后加载插件树**，插件 `apply` 崩掉时端口已经能回 HTTP。所以"就绪"的判据是**三条同时满足**：端口有 HTTP 响应 + 实例日志出现正向就绪行（`dsh web: http://127.0.0.1:<port>/?token=…`）+ 进程仍存活；并全程扫描致命启动特征（`plugin tree failed to load` / `failed to apply|import loader entry` / `without inject` / `cannot get property` / `missed the module table` / `duplicate loader entry`），命中即 `exit 1` 并打印**崩溃栈关键行 + 隔离实例日志路径**。旧实现只看"端口回了 HTTP"，于是「实例整个起不来」被报成 `✓ 实例启动就绪 / ✓ 启动日志无 error`（#298 的 P0 正是这样潜伏到用户侧的）
    - **崩溃证据在哪**：隔离 `DSH_HOME/dsh-web.log`（脚本用 `stdio: ['ignore', fd, fd]` 把实例 stdout/stderr 落盘）。失败时脚本会打印该路径与摘要；排查时**先读它**，不要只看脚本控制台 —— 崩溃栈可能晚于脚本读日志才落盘
  - **`dsh.client.external` 校验（issue #294，1c 内）**：external 是「同 boot 图内的跨插件 client 行请求」，缺包时无 stub、无隔离（整条 client factory 抛错 → 插件 UI 全挂）。门禁断言：① 每个 external 项必须在 `dependencies` 或 `peerDependencies` 声明（否则阻断）；② 指向**仓库内**插件时——在 `dependencies` 的走既有「已发布 + 已打 tag」检查（复用 `findUnpublishedDeps`，**不要求**降级声明），**仅**在 `peerDependencies` 的必须同时在 `dsh.client.externalDegraded` 里显式声明「缺失时有降级路径」（`"dsh": {"client": {"external": ["dsh-md-render"], "externalDegraded": ["dsh-md-render"]}}`），未声明即阻断。冗余的 `externalDegraded` 声明（不在 external 中）只打印 info、不阻断。**为什么不要求"移进 dependencies"**：`dsh plugin add` 只把 **profile 直接 dependencies** 里声明 `dsh.bundle.patch` 的包写进 `dsh.profile.bundles`；插件自己的 dependency 只被 pnpm 铺到 `profile/node_modules`（hoisted），不会进 profile 的 dependencies、不会被 reconcile 激活 → 无 client graph row，浏览器 `require` 依旧落空 —— 即"移进 deps"只是落盘的形式合规，真实行为与 peer-only 相同，要求它等于用形式合规换放行，抓不到 #290/#293 这类崩溃。宿主解析 `dsh.client` 只认 `platform` / `inject` / `external` / `immediately`，**未知字段一律丢弃** → 新增 `externalDegraded` 对运行时安全（纯门禁契约元数据）。纯函数 `checkClientExternals` / `listDegradedExternals` / `findRedundantDegradedExternals`，单测在 `scripts/test/release-checks.test.mjs`
  - **3c 缺包演练（issue #294，防"结构性假通过"）**：隔离实例过去无条件复用生产 profile 的全部 `node_modules`，本机已装 `dsh-md-render` 时「新装用户没装它」这个状态**永远验证不到**（实测 #294 之前对 `dsh-think-zh-expand` 恒通过）。现在 3c 默认传 `--clean-externals`：从 `--addons` 的 `dsh.client.external` 推导缺失集合，该集合**既不复用真实 profile、也不做 addon 链接**，并同时从隔离 profile 配置（`dependencies` + `dsh.profile.bundles`）剔除（只删 node_modules 会得到「配置列着却装不上」的不一致状态，boot 阶段直接 `cannot resolve profile bundle` 起不来）；启动前 `checkOmittedAbsent` fail-closed 校验"确实不可解析"，日志扫描覆盖 `failed to import loader entry` / `missed the module table` / `Element type is invalid` / `Cannot find module`。另有 `--omit-node-modules <pkg>` 显式排除条目（环境噪声隔离用）。**边界**：client 侧渲染崩溃发生在浏览器运行时，server 日志未必留痕 —— 这一项仍需浏览器步骤（`skills/verifying-dsh-plugins`）兜底
  - README 效果截图引用有效（`./assets/` 相对路径 或 `https://unpkg.com/<包名>/assets/` 绝对 URL，文件必须真实存在）；**无用户可见 UI 的插件**按显式声明豁免（`package.json` 的 `dsh.ui=false` + 非空 `dsh.uiReason`；`dsh.kind=library` 的共享工具包沿用原豁免），豁免结果在发版输出与批量汇总中显式列出（issue #227）
  - **`--all-checks`（仅 dry-run，issue #227）**：静态门禁（peer / 跨插件依赖 / CHANGELOG / 测试 / 效果图）全部跑完再统一报告失败项——避免 fail-fast 让后续门禁「从未执行」而掩盖缺陷；`--push` 仍走首个失败即停的完整门禁
  - CHANGELOG 有当前版本段
- 预览：`cd plugins/<名> && npm pack --dry-run`（tarball 内容清单，防 secrets 泄露）

| 通道           | 触发                                                     | 说明                                                    |
| -------------- | -------------------------------------------------------- | ------------------------------------------------------- |
| GitHub Release | tag 推送（release.yml）                                  | 自动打包 tgz + CHANGELOG 作为 release notes             |

## 踩坑记录

| 现象                          | 原因 / 处理                                                                                                                                                                                                                                       |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `git tag` 已存在              | 该版本号发过版（tag 指向旧代码）→ bump 到新版本号；不要 force 覆盖旧 tag                                                                                                                                                                          |
| release workflow 版本校验失败 | tag 指向的提交里 package.json 版本 ≠ tag 版本 → 必须先提交 bump 再打 tag（`--bump --push` 已保证）                                                                                                                                                |
| npm `ENEEDAUTH`               | 环境变量 `npm_config_registry`（镜像）覆盖配置 → 用 `--userconfig "$NPMRC" --registry "$NPMREG"` 双参数（npm-ops skill）                                                                                                                          |
| npm `E403` 2FA                | 用 bypass 2fa 的 Granular Access Token；或 `--otp=<验证码>`（30 秒时效，多包易超时）                                                                                                                                                              |
| npm `E409` staged version     | 版本已发布/部分发布 → `npm view <pkg> versions` 确认，bump 后再发                                                                                                                                                                                 |
| 发版后文档不同步              | CI 的 `check-docs.mjs` 已强制（根 README 插件表 / docs 索引与模块 / 安装章节）                                                                                                                                                                    |
| 插件名写错 / 用旧名发版       | Actions 入口：`Resolve + validate plugins` 步骤 fail-fast，报 `非法插件名: …` 并列出允许值（旧名如 `dsh-notify` 已改名，不在允许值内）；本地脚本：`✗ plugins/<名字> does not exist`                                                               |
| 发版"卡住"很久不动            | 瓶颈是 3c 隔离实例冷启动（~8.7s，占全链路 73%）与 1a 的 npm 查询（未发布包 E404 分支可达 2.5s）；看脚本末尾的阶段耗时表定位，不要盲猜                                                                                                             |
| 并发发版后出现"孤儿"隔离实例  | `verify-real-profile.mjs` **没有信号清理**：中途强杀（Ctrl-C / kill / 提前 return）会残留实例与 `/tmp/dsh-verify-real-*/`；因此并发门禁**必须 await 完**才退出，失败路径也不提前返回——见 [踩坑/发版并发化的两个坑](../踩坑/发版并发化的两个坑.md) |
| 并发发版时两个实例抢同一端口  | 原实现是每个插件内部各自 `findFreePort(3087)`，串行不会撞、并行必撞；现在由调度层用 `findFreePorts` 预分配互不相同的端口                                                                                                                          |
| 3c"秒过"（0.2s 就绪）         | 残留隔离实例占着同一端口，而就绪探测只认「任何 HTTP 响应」→ 验的其实是他人实例（真实冷启动 ~8s，#294 实测）。现在启动前 `isPortInUse` **fail-closed**：端口被占直接报错，不把他人实例当验证结果                                                   |
| 缺包演练只删 node_modules     | 配置里仍列着该 bundle ⇒ boot 阶段抛 `cannot resolve profile bundle "dsh-md-render"`，实例起不来、反而验不到"缺包能否降级"（#294 实测）。必须连 `dependencies` + `dsh.profile.bundles` 一起剔除（`stripProfileDeclarations`）                      |

## 自动化覆盖（防复发）

| 环节                                       | 机制                                                                                                                                                                                                                                      |
