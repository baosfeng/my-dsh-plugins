# 工程效率规范（DX）

> issue #240。本文件是「让日常开发循环更快」的**唯一权威规范**：五条效率原则、性能瓶颈的处置流程、
> leader 的职责边界、任务的完成判据、以及「验证链路可信性」的硬要求。
> 精简条目在 [AGENTS.md](../../AGENTS.md)，按需加载入口在 skills，**三层缺一不可**（见文末「文档即规范」）。

## 为什么需要这份规范

owner 的原话：

> 优化一下速度，比如 hook 速度、发版速度、流程速度等等等等阻塞性的环节，不要把时间浪费在这里，
> 后续每一个子 agent 开发都要耽搁时间在这上面，可以形成流程的就流程，可以自动化的就自动化，
> 可以并行的就并行，可以早点提交的就提交，可以流水线处理的就流水线处理。

本仓库的工作模式是 **1 个 leader（主 agent）+ 最多 3 个子 agent 并行**，每个子 agent 的开发循环是：

    fork 池创建 → 改代码 → 跑插件测试 → commit（pre-commit）→ push（pre-push）
    → 建 PR → 等 CI 绿 → 合并 → 清理 fork

**这个循环里的每一秒，都要乘以本仓库历史上已发生的几十次子任务。** 所以哪怕只省 20 秒，
累计收益也很可观；反过来，一个每次都踩的坑（哪怕只耽误 1 分钟）就是**结构性亏损**。

## 一、能流程化的就流程化

**判据：同一套手工步骤重复 ≥ 2 次，就必须变成脚本。** 不是"有空再抽"，而是"第二次做的时候就抽"。

| 手工过程                             | 固化成                                                | 效果                                                  |
| ------------------------------------ | ----------------------------------------------------- | ----------------------------------------------------- |
| fork 池 5 步 + 手工软链 node_modules | `node scripts/fork-pool.mjs create <编号>`            | 人工 5 步（约 7s 命令 + 易漏前置）→ **一条命令 3.3s** |
| 提交前跑一堆检查                     | `node scripts/verify-local.mjs --fast`                | 按变更裁剪，纯文档 0.5s、改一个插件 10.7s             |
| 逐插件测试                           | `bash scripts/test-all.sh [插件...]`                  | 汇总式跑完，不再 fail-fast 掩盖后续失败               |
| 版本 bump + CHANGELOG + tag + push   | `node scripts/release.mjs <插件> --bump patch --push` | 批量发版一次提交、顺序打 tag                          |
| 推送前"环境到底行不行"               | `node scripts/fork-pool.mjs check`                    | 四个 yes/no，结论首行可读                             |

**反面案例**：本专项开始前，fork 池的创建/清理是 skill 里的一段手工命令，每个子 agent 都要重敲一遍；
其中"装 hooks"这一步**从来没人做**（因为没人知道要做），于是所有子 agent 的本地门禁都是空转的
—— 这就是"手工步骤里最容易漏掉的那一步，一定会被漏掉"。

## 二、能自动化的就自动化

**判据：人肉检查点能变成机器判定的，就变成机器判定。** 靠"记得做"的事情，等于没有。

| 人肉检查点                            | 机器判定                                                        | 落在哪                  |
| ------------------------------------- | --------------------------------------------------------------- | ----------------------- |
| "记得提交前跑 prettier"               | lint-staged 在 pre-commit 自动 `--fix` / `--write` 并重新 stage | `.husky/pre-commit`     |
| "记得提交信息用 conventional commits" | commitlint 在 commit-msg 拦截                                   | `.husky/commit-msg`     |
| "记得推送前跑全量校验"                | pre-push 自动 `verify-local --fast`                             | `.husky/pre-push`       |
| "fork 环境到底能不能跑校验"           | `fork-pool check` 的四个断言                                    | `scripts/fork-pool.mjs` |
| "文档改了要同步索引/链接"             | `check-docs.mjs` + `check-links.mjs`                            | CI `quality` job        |

**关键前提**：自动化只有在**它真的会运行**时才有价值。本专项修掉的最大缺陷就是
"钩子看起来装了、实际上没生效"（详见 [踩坑：fork 池钩子与工具链未就绪](../踩坑/fork池钩子与工具链未就绪.md)）。
**自动化机制本身也要有判据**：`fork-pool check` 会明确回答"`core.hooksPath` 是什么、工具链能不能解析"。

## 三、能并行的就并行

**并行度上限 3 个子 agent**（AGENTS.md 强制）。除了人，机器侧也有并发：

- `verify-local` 检查项并发 4 / 插件测试并发 6（issue #188 实测调优：并发 3 → 6 省 6.1s；并发 8 无收益，
  瓶颈是"最慢的那个插件"）。本机 10 核（`sysctl -n hw.ncpu`），3 个子 agent 各跑 6 路插件测试 =
  18 个测试进程，**已经超卖**，这正是下面那条禁令的由来。
- CI 的 19 个插件 matrix job 天然并行。

**什么绝对不能并行**（踩过的坑，见 [多 agent 并行测试资源冲突](../踩坑/多agent并行测试资源冲突.md)）：

- **同一插件的测试进程**：`vitest --coverage` 会争用该插件的 `coverage/` 临时目录，
  表现为 `EACCES/ENOENT` 或 5s 联网用例超时，实测两个 agent 同轮 `EXIT=124`。
  `verify-local` 内置"疑似并发冲突 → 串行复测一次"的降级，但**根因是别并行**。
- **同一插件的发版**：tag / npm 发布是单向外发动作，并发必然冲突。
- **同一个 fork 目录**：一个 fork = 一个子任务 = 一个分支 = 一个 PR。

## 四、能早点提交的就提交

**小步提交、早推 PR，让 CI 与本地后续工作并行。** 不要攒一个大 PR 到最后。

- 每完成一个**可独立验证**的优化就 commit + push（本专项自身就是这么做的：脚本、pre-commit、
  隔离实例修复各自独立提交）。
- **推 PR 不等于完工**：push 后立刻开 PR，让 CI 先跑起来，本地继续做下一件事；
  CI 在跑的那 70~80 秒不该是"干等"。
- **反模式**：把所有改动攒成一个巨型 PR → CI 一次红一片、定位成本指数上升、
  中途 rebase 冲突不断、review 与验收都无法分段进行。

## 五、能流水线处理的就流水线处理

把**串行等待**改成**流水线**：

| 串行（旧）                           | 流水线（推荐）                                       | 收益                           |
| ------------------------------------ | ---------------------------------------------------- | ------------------------------ |
| 本地跑完全量校验 → 再 push → 再等 CI | push 后立刻开 PR，CI 与本地后续工作并行              | 省掉整段"干等 CI"的墙钟        |
| 一次只发一个插件                     | `node scripts/release.mjs a b c --bump patch --push` | 独立校验、一次提交、顺序打 tag |
| 一个子任务做完再派下一个             | 最多 3 个 fork 并行（物理隔离）                      | 墙钟 ≈ 最慢的那个              |

## 六、性能瓶颈零容忍

**判据：任何让日常操作变慢的环节都是缺陷** —— 立卡、测量、优化，不等用户抱怨。

铁律：**优化必须有 before/after 实测数字，禁止只讲道理**。基线表如下（本机实测，issue #240）：

| 环节                                             | before                              | after / 现状      | 备注                                                                      |
| ------------------------------------------------ | ----------------------------------- | ----------------- | ------------------------------------------------------------------------- |
| fork 创建（人工 5 步）                           | 约 7s 命令时间 + 每次可能漏装 hooks | **一条命令 3.3s** | clone 241ms / fetch 1.5s / 基线校验 1.5s / node_modules 28ms / hooks 73ms |
| node_modules 就位                                | shell 循环 3657ms                   | **29ms**          | Node `readdirSync` 逐包软链；shell glob 还会漏 `.bin`                     |
| commit（门禁生效前提下）                         | 1156ms                              | **802ms**         | commit-msg 直调后 992ms，pre-commit 也直调后 802ms                        |
| `verify-local --fast`（改一个叶子插件）          | —                                   | 10.7s             | 只跑受影响插件                                                            |
| `verify-local --fast`（纯文档）                  | —                                   | 0.5s              | 按范围跳过 9 项                                                           |
| `verify-local --fast`（改 `scripts/`）           | —                                   | 7.0s              | 跑 10 项检查                                                              |
| `verify-local --fast`（改 dsh-shared，安全退化） | —                                   | 23.6s             | 16 个插件受影响 → 裁剪无意义，全量                                        |
| push（SSH 传输）                                 | —                                   | 约 3.7s           | 与校验耗时叠加                                                            |
| 一轮 CI 墙钟                                     | —                                   | 71~79s            | 23 个 job 并行；单 job 的 `npm ci` 约 18s                                 |

**"退化全量"不是 bug，是安全设计**：没有变更证据时宁可全量，绝不静默放水（见
[构建与测试](构建与测试.md)「本地一键校验」）。

### 优化时不许削弱门禁

要快，但**该挡的必须照样挡住**。本专项的取舍写在这里，供后人复用：

| 做法                                         | 代价                                                      | 收益                                                                                                       | 结论                                                                                     |
| -------------------------------------------- | --------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| fork 内默认装 hooks（pre-commit + pre-push） | commit +0.77s/次，push +0.5s（纯文档）~+23.6s（退化全量） | 一次漏检事故 = 一轮 CI 白跑约 80s + 人工翻日志定位（保守 300s）+ 修复重推 + 再等一轮约 80s ≈ **460s 以上** | **默认装**。一次事故的代价够付约 570 次提交的开销                                        |
| `npx` → 直调 `node_modules/.bin/*`           | 需要保留 fallback（见下）                                 | 每次提交省约 174ms                                                                                         | **做**。但 `.husky/` 脚本文本不能把命令简化成变量，否则 knip 报 `Unused devDependencies` |
| `fork-pool create --no-hooks`                | 本地门禁空转                                              | 省 commit 0.77s/次                                                                                         | **仅用于一次性脚本化操作**；日常开发不要用                                               |

> ⚠️ `--no-hooks` 不是"快速模式"，它是"我知道自己在放弃本地门禁"。用了它就必须在推送前跑
> `node scripts/fork-pool.mjs check`（它不依赖 hook，会真的跑 `verify-local --fast`）。

## 七、验证链路可信性（不可信的验证环境比没有验证更糟）

**核心论点：一个会给出错误结论的本地环境，比"没有本地验证"更危险** —— 前者让你以为验过了。

两条实测教训（都花掉了别的 agent 大量时间）：

1. **fork 里 `.bin` 缺失** → `npx --no-install vitest` / `depcruise` 解析失败 →
   verify-local 里若干检查项报错，被误读成"我的代码有问题"。
   根因是 shell glob `node_modules/*` 不匹配点号开头的名字，`.bin` 整条漏掉。
2. **隔离实例被插件自己关掉插件** → dshmarket 把启停状态写在
   `profiles/<profile>/.dsh-market/state.json`，启动时按它强制 off；
   复刻生产 profile 时若一起复制，隔离实例就"继承"了生产的禁用名单 →
   client bundle 不进 manifest、server API 404，看起来像插件坏了。
   详见 [踩坑：隔离实例插件被静默禁用](../踩坑/隔离实例插件被静默禁用.md)。

**fork 环境自检清单（一条命令，四个 yes/no）**：

```bash
cd /tmp/gh-fork-<编号>
node scripts/fork-pool.mjs check          # 完整自检（含 verify-local --fast）
node scripts/fork-pool.mjs check --static # 只做静态四项，秒级
```

| 断言                  | 判据                                                                          | 不通过时的含义                                          |
| --------------------- | ----------------------------------------------------------------------------- | ------------------------------------------------------- |
| hooks 已挂载          | `core.hooksPath = .husky/_` 且 `.husky/_` 存在                                | 提交/推送不会跑本地门禁（PR #239 的 prettier 红盘根因） |
| 工具链可解析          | `node_modules/.bin` 下有 vitest / depcruise / prettier / eslint / cucumber-js | "跑了但失败"不可信，别去改代码                          |
| 基线未过期            | fork 的 `origin/main` == `git ls-remote origin refs/heads/main`               | 分支基于旧 main，PR 会混入无关差异                      |
| node_modules 未误暂存 | 暂存区里没有 `node_modules` 相关项                                            | `git add -A` 会把软链当新文件提交（体积事故）           |

## 八、leader 的职责边界

leader（主 agent）**只做拆解、派发、验收、汇报**。

- 调查 / 测量 / 优化 / 排查 / 翻日志 / 跑命令 / 写文档 —— **一律派子 agent**。
- 亲力亲为 = 占用最稀缺的上下文资源 = 失职。
- **唯一例外**：特别简单、且**派发开销 > 自做开销**的小事。典型是"改一行配置""回复一句确认"
  —— 派发的 prompt 要写清背景、约束、验收标准，写完的时间早就把事做完了。
  **判据就是这一句：派发开销 > 自做开销。**

## 九、任务必须有明确的完成判据与停止条件

派任务时必须**同时**给出三样东西：

1. **验收判据**：达成什么算完成；
2. **停止条件**：什么情况下**明确不需要**继续做；
3. **交付节奏**：先提交可工作版本，再迭代补充（对应第四节"早点提交"）。

**真实反面案例**：一个子 agent 修好了 CI flaky（确定性 RED→GREEN、目标用例 25 轮 0 失败、全量绿），
却继续花大量时间追查"另一个**基线本来就存在**的既有 flaky 归属"，迟迟不提交 ——
验收判据其实早就满足了。

反模式清单：

| 反模式                       | 正确做法                                                 |
| ---------------------------- | -------------------------------------------------------- |
| 基线既存问题混进本次修复范围 | 证明它与本次改动无关（基线同样失败）后**记录并移出范围** |
| 为"更保险"重复跑 N 轮        | 达到约定轮数即停（如"目标用例 25 轮 0 失败"）            |
| 追求"完全确认"才提交         | 先提交可工作版本，剩余问题另开                           |
| 把验证当无限工程             | 验证有明确终点：判据满足即结束                           |

**判据示例**（可直接抄）：

- 修 flaky：**"改动前 RED / 改动后 GREEN + 目标用例 N 轮 0 失败"即达标**。
- 修门禁失效：**"故意违规的提交被拦住 + 合法提交仍通过"即达标**。
- 性能优化：**"before/after 都有实测数字，且门禁未削弱"即达标**。

## 十、并行工作必须有信号共享

多个 agent 同时干活时，**同一件事被做两遍**是最常见的浪费。

**真实案例**：本专项进行期间，另一个 agent 独立踩到同一个 fork hooks 坑并在自己的 PR 里修了
`skills/dsh-github-triage/SKILL.md`；leader 发现后才广播协调，避免了两份重复的论证。

机制：

- 开工前在 issue 里认领，写清"我要动哪些文件"；
- leader 发现两条线撞车时**立刻广播**（而不是等两边都做完）；
- 撞车时的处理原则是**去重而不是覆盖**：后到的一方保留先到方的证据链，只补对方没有的部分
  （例如本专项保留了 SKILL.md 里的手工兜底说明，只把主路径换成脚本）。

## 十一、文档即规范（三层缺一不可）

新增规范必须落到三层，否则**等于没写**：

| 层       | 位置                                   | 放什么                             | 加载方式         |
| -------- | -------------------------------------- | ---------------------------------- | ---------------- |
| 精简条目 | [AGENTS.md](../../AGENTS.md)（≤50 行） | 一句话原则 + 指向详细文档          | 每次会话自动注入 |
| 按需加载 | `skills/*/SKILL.md`                    | 触发条件 + 关键命令 + 交叉引用     | 命中场景时加载   |
| 详细     | `docs/`（本文件）                      | 为什么、怎么做、实测数据、反面案例 | 需要时读         |

**判据**：只在 `docs/` 写了一份规范、没进 AGENTS.md、也没被任何 skill 引用 = 没写。
新脚本同理 —— **引入即生效**：它必须在 skill 或流程里被真正引用（例如
[fork 池创建](../../skills/dsh-github-triage/SKILL.md) 指向 `scripts/fork-pool.mjs`），不能只是躺在 `scripts/` 里。
