# 工程效率规范（DX）

> **何时阅读**：设计/优化开发流程、发现某个环节拖慢日常循环、给子 agent 派任务时。
> 精简条目在 [AGENTS.md](../../AGENTS.md)，按需加载入口在 skill，详细理由与踩坑证据在本文件与 [踩坑目录](../踩坑/README.md)。

## 一、能流程化的就流程化

**判据：同一套手工步骤重复 ≥ 2 次，就必须变成脚本。**

| 手工过程                            | 固化成                                                            |
| ----------------------------------- | ----------------------------------------------------------------- |
| fork 池创建 + 手工软链 node_modules | `node scripts/fork-pool.mjs create <编号>`（含装 hooks）          |
| 提交前跑一堆检查                    | `node scripts/verify-local.mjs --fast`（按变更裁剪）              |
| 逐插件测试汇总                      | `bash scripts/test-all.sh [插件...]`（不 fail-fast 掩盖后续失败） |
| 版本 bump + CHANGELOG + tag + push  | `node scripts/release.mjs <插件> --bump patch --push`             |
| 推送前环境自检                      | `node scripts/fork-pool.mjs check`                                |

**手工步骤里最容易漏掉的那一步，一定会被漏掉**——所以关键步骤不进文档、进脚本。

## 二、能自动化的就自动化

**判据：人肉检查点能变成机器判定的，就变成机器判定。靠"记得做"的事情等于没有。**

- 格式化 → lint-staged 在 pre-commit 自动 `--fix` / `--write` 并重新 stage；提交信息规范 → commitlint 在 commit-msg 拦截；推送前校验 → pre-push 自动 `verify-local --fast`。
- 环境自检 → `fork-pool check` 的四项断言；文档同步 → 文档一致性 + 引用完整性检查进 CI `quality` job。

**自动化只有在它真的会运行时才有价值**：钩子看起来装了、实际没生效是发生过的最大缺陷（[踩坑目录](../踩坑/README.md)「fork 池：基线过期与钩子未生效」）。自动化机制本身也要有判据。

## 三、能并行的就并行

- 子 agent 并行上限 **3**（AGENTS.md 强制）；`verify-local` 检查项并发 4、插件测试并发 6。
- CI 的 19 个插件 matrix job 天然并行。

**绝对不能并行**：

- **同一插件的测试进程**：`vitest --coverage` 争用该插件 `coverage/` 临时目录，表现为 `EACCES/ENOENT` 或联网用例超时；`verify-local` 有串行复测降级，但根因是别并行（见 [踩坑目录](../踩坑/README.md)「测试随机失败：固定 sleep 与并行撞锁」）。
- **同一插件的发版**：tag / npm 发布是单向外发动作，并发必冲突。
- **同一个 fork 目录**：一个 fork = 一个子任务 = 一个分支 = 一个 PR。
- **全量门禁**：与任何并行写操作互斥 —— 同一时刻最多 1 路，见 [leader 行为规范](leader行为规范.md) 第六节。

## 四、能早点提交的就提交

**小步提交、早推 PR，让 CI 与本地后续工作并行。**

- 每完成一个**可独立验证**的优化就 commit + push。
- push 后立刻开 PR，CI 跑的那 70~80 秒不该是干等。
- 反模式：攒成巨型 PR → CI 一次红一片、定位成本指数上升、rebase 冲突不断、验收无法分段。

## 五、能流水线处理的就流水线处理

把**串行等待**改成**流水线**：本地跑完全量 → push → 等 CI 的串行链，换成 push 后立刻开 PR（CI 与本地并行）；批量发版用一条命令（独立校验、一次提交、顺序打 tag）；并行 3 个 fork（墙钟 ≈ 最慢的那个）。

```bash
node scripts/ship.mjs -m "fix(x): 修好" --dry-run              # 先看计划（不外发任何东西）
node scripts/ship.mjs -m "fix(x): 修好" --push --pr --issue N  # 提交 + 推送 + 开 PR
```

安全模型：**默认什么都不外发**（`--push` / `--pr` 才是显式同意参数）、拒绝在 `main`/`master` 上执行、**本地校验失败则不建 PR**。它用 `--no-verify` 跳过 pre-push（否则钩子会串行再跑一遍 verify，"与 CI 并行"无从谈起），但自己一定会跑 `verify-local --fast`——门禁没被削弱，只是从"推送前阻塞"改成"推送后并行"。

## 六、性能瓶颈零容忍

**判据：任何让日常操作变慢的环节都是缺陷——立卡、测量、优化，不等用户抱怨。** 铁律：**优化必须有 before/after 实测数字，禁止只讲道理。**

**"退化全量"不是 bug，是安全设计**：没有变更证据时宁可全量，绝不静默放水（见 [构建与测试](构建与测试.md)「本地一键校验」）。

### 优化时不许削弱门禁

- **fork 内默认装 hooks**（pre-commit + pre-push）：一次漏检事故的代价（CI 白跑 + 人工定位 + 重推）远高于每次提交的固定开销。
- **`npx` → 直调 `node_modules/.bin/*`**：做，但 `.husky/` 脚本不能把命令简化成变量，否则 knip 报 `Unused devDependencies`。
- **`fork-pool create --no-hooks`** 不是"快速模式"，是"我知道自己在放弃本地门禁"：仅用于一次性脚本化操作，用了就必须在推送前跑 `node scripts/fork-pool.mjs check`。

## 七、验证链路可信性（不可信的验证环境比没有验证更糟）

**一个会给出错误结论的本地环境，比"没有本地验证"更危险**——它让你以为验过了。两类实测陷阱：**fork 里 `.bin` 缺失**（`npx --no-install vitest` / `depcruise` 解析失败，被误读成"我的代码有问题"；根因是 shell glob `node_modules/*` 不匹配点号开头的名字）；**隔离实例被插件自己关掉插件**（dshmarket 把启停状态写在 profile 的 `.dsh-market/state.json`，复刻生产 profile 时一起复制就"继承"了生产的禁用名单，看起来像插件坏了，见 [踩坑目录](../踩坑/README.md)「隔离实例假验证（软链复用与静默禁用）」）。

```bash
cd /tmp/gh-fork-<编号>
node scripts/fork-pool.mjs check           # 完整自检（含 verify-local --fast）
node scripts/fork-pool.mjs check --static  # 只做静态四项，秒级
```

| 断言                  | 判据                                                                          | 不通过时的含义                     |
| --------------------- | ----------------------------------------------------------------------------- | ---------------------------------- |
| hooks 已挂载          | `core.hooksPath = .husky/_` 且 `.husky/_` 存在                                | 提交/推送不会跑本地门禁            |
| 工具链可解析          | `node_modules/.bin` 下有 vitest / depcruise / prettier / eslint / cucumber-js | "跑了但失败"不可信，别去改代码     |
| 基线未过期            | fork 的 `origin/main` == `git ls-remote origin refs/heads/main`               | 分支基于旧 main，PR 会混入无关差异 |
| node_modules 未误暂存 | 暂存区无 `node_modules` 相关项                                                | `git add -A` 会把软链当新文件提交  |

## 八、leader 职责与派发

leader 职责边界、派发闸门（耗时 / 工作量判据）、自执行熔断、验收与发版归属、偏差处置见 [leader 行为规范](leader行为规范.md)。

## 九、任务必须有明确的完成判据与停止条件

派任务必须**同时**给：① 验收判据（达成什么算完成）；② 停止条件（什么情况下明确不需要继续做）；③ 交付节奏（先提交可工作版本，再迭代补充）。

反模式与对策：基线既存问题混进本次范围 → 证明与改动无关（基线同样失败）后记录并移出；为"更保险"重复跑 N 轮 → 达到约定轮数即停；追求"完全确认"才提交 → 先交可工作版本、剩余另开；把验证当无限工程 → 判据满足即结束。

判据示例：修 flaky = 「改动前 RED / 改动后 GREEN + 目标用例 N 轮 0 失败」；修门禁失效 = 「故意违规的提交被拦住 + 合法提交仍通过」；性能优化 = 「before/after 都有实测数字且门禁未削弱」。

## 十、并行工作必须有信号共享

多个 agent 同时干活时，**同一件事被做两遍**是最常见的浪费。开工前在 issue 里认领并写清"我要动哪些文件"；leader 发现两条线撞车时**立刻广播**；撞车处理原则是**去重而不是覆盖**——后到方保留先到方的证据链，只补对方没有的部分。

## 十一、文档即规范（三层缺一不可）

三层缺一不可：**精简条目**放 [AGENTS.md](../../AGENTS.md)（≤50 行，一句话原则 + 指向详细文档，每次会话自动注入）；**按需加载**放 skill 的 SKILL.md（触发条件 + 关键命令 + 交叉引用）；**详细**放 `docs/`（本文件：为什么、怎么做、实测数据、反面案例）。

**判据**：只在 `docs/` 写了规范、没进 AGENTS.md、也没被任何 skill 引用 = 没写。新脚本同理——**引入即生效**，必须在 skill 或流程里被真正引用。

## 十二、issue / PR 的处置必须反馈（不得静默）

任何 issue / PR 的**合并 / 不合并**决策（合并、squash、关闭、暂缓、放弃、拆分、改范围、转为分析结论）都必须**逐条反馈用户**并公开留痕：

- **必须带三要素**：① 对象（编号 + 链接）② 决策 ③ 理由一句话（含门禁结果或证据）。
- **反馈 ≠ 请示**：全权委托下 leader 仍自主拍板先做，差别只在做完必须逐条说清；只有架构级 / 破坏性 / 公开 API 变更事前请示。
- **未合并要写解锁条件**（什么条件下再推进），否则等于静默丢弃；**双通道留痕**（用户可见的处置表 + `ghops pr comment` / `ghops issue comment`）。
- **禁止**：只报「完成 N 项」不说哪些没合并、为什么；无评论静默关闭；PR 长期 open 无人问津。
- **验收**：每轮汇报必须出现处置表（对象 / 决策 / 理由 / 链接），缺失即视为未反馈。

## 十三、输出必须精简，超限就截断（禁止刷屏）

面向人的输出（leader 汇报、子 agent 回报、机器人 review 评论、CI/PR 评论）都必须**结论优先、可扫读**；超出上限必须**截断并指向完整来源**（"完整结果见 <CI 日志 / artifact 链接>"）。**宁可截断，也不全量发出。**

- 机器人评论硬上限：总长 ≤30 行、关键证据 ≤5 条，超出即截断。
- 不堆原始输出、不贴大段日志或 HTML、同一结论不重复表述。
- leader 汇报只讲「做了什么 / 结论 / 下一步 / 需要用户决策的点」，细节留在 issue、PR、日志。

## 十四、本地必须能拦住 CI 能拦的一切（本地绿 ⇒ CI 绿）

CI 的每一个**阻断性**检查都必须在本地有对应项**并默认执行**。出现「本地全绿、CI 却红」是**门禁缺陷，必须定位并修掉**（补本地检查 / 修 flaky / 显式白名单），不得当成"CI 抽风"。

- **默认路径**：推送前默认跑 CI 等价集合（`npm run verify`）；提速不能以牺牲这条为代价。
- **裁剪纪律**：允许按变更裁剪，但裁剪必须有证据；无证据时安全退化为全量；走快速通道必须明确打印「本次未跑 X/Y/Z，CI 会跑」。
- **豁免白名单**：确实无法本地执行的（矩阵 OS/Node 版本、CI 专属凭据、覆盖率上报）必须显式白名单 + 理由，写在可校验的配置里；「本地慢」不是理由。
- **双向校验**：①「CI 有、本地无」②「本地有、CI 无」③「注册了但从未被调用」——三种都要有失败用例。
- **merge ref**：GitHub 在 PR 上测的是**合并结果**，本地测自己的分支；该差异必须消除或显式化为一条本地检查。
- **flaky 同罪**：时序 flaky 导致的「本地绿、CI 红」同样违反本规则，修 flaky 与加本地检查同等优先。
- **全局状态**：测试与检查不得依赖全局共享资源（`os.tmpdir()` 计数、固定端口、共享目录/单例文件）；不能区分「我创建的」与「别人正在用的」就必须注入专属作用域。
- **校验自身**：上述一致性校验必须在 CI 里执行，否则校验自己就成了第四种漏网形态。

**反向同样成立**：出现「本地红、CI 绿」（假红）也是缺陷——假红会训练人忽略门禁。最常见来源是依赖全局共享状态（本地多进程并发，CI 单进程则结论分裂）。

## 十五、全量门禁单点、负载熔断与委派纪律

同一时刻最多 1 路全量门禁（含启动前的负载熔断阈值、派发时间盒与 leader 巡检义务）见 [leader 行为规范](leader行为规范.md) 第六节；默认委派闸门、自执行熔断与验收 / 发版边界见同文第二、三、四节。
