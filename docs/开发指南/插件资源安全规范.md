# 插件资源安全规范

> ⚠️ **何时阅读：** 开发/修改插件的 server 端持续运行逻辑（事件监听、持久化、轮询、流处理、后台任务）前必读。
> 先读 [resource-budget-review](../../skills/resource-budget-review/SKILL.md) 与本文档，评审完五个资源维度（IO/CPU/内存/网络/磁盘存量）才算完成。

## 1. 核心原则

1. **正确 ≠ 便宜**：功能测试通过只证明"它工作"，不证明"它便宜"——资源成本（写放大 / CPU / 内存）必须**显式评估并用数字守住**，最好有自动化断言。
2. **先选对持久化原语，再谈优化**：原语错配是写放大事故的根源（事件流用全量快照原语）。
3. **监控是降级的先决条件，降级是监控的目的**：只告警不动作 = 事故仍要等人手动介入。
4. **降级必须可恢复、有界**：降级动作保证内存/文件有界，资源回落后自动恢复，且不丢失降级前数据。

## 2. 高频写路径分级与模式选型

| 形态           | 特征                         | 持久化原语                                               |
| -------------- | ---------------------------- | -------------------------------------------------------- |
| **事件流型**   | 高频追加、每条独立、总量增长 | **增量 append（jsonl）+ 周期 compact**                   |
| **状态快照型** | 低频全量、整体替换、数据汇总 | **写入调度 + 原子写**（默认护栏 1s 节流 / 1MB 字节上限） |
| **计数器型**   | O(1) 更新、无跨会话累积结构  | 内存维护 + 低频快照（>10s 节流）                         |
| **无状态型**   | 不需要持久化                 | 不落盘，纯内存（注意内存上限）                           |

> **判定口诀**：**事件流型禁止用全量快照原语**（写放大 = 状态大小/事件大小，数百~数千倍）；状态快照型禁止高频触发（防抖 + 节流窗口 + 字节上限）。

### 2.1 事件流型（最高风险）

用 `dsh-shared` 的 `jsonlAppender`（`plugins/dsh-shared/lib/jsonl.js`）：`{ flushMs: 500, compactLines: 5000, logger, onCompact }`——`flushMs` 防抖批量 append（写放大 ≤ 1 + 小系数），`compactLines` 行数阈值触发宿主原子 compact，`onCompact` 里 `store.snapshot(renderAllLines())` 由内存全量生成行。`store.append(event)` 高频只入队；卸载时 `store.dispose()` 冲刷挂起数据。

必须满足：落盘字节 ≈ 事件本体字节（禁止整桶全量重写）；有**字节上限**（compact/轮转），不是只有条目上限；加载解析容错（坏行跳过不崩溃）；内存有上界（条目上限 + 全局上限，FIFO 淘汰）。

### 2.2 状态快照型

用 `dsh-shared` 的 `createWriteScheduler` + `atomicWriteJson`（`lib/{scheduler,persist}.js`）：`createWriteScheduler({ logger, write: ({ force }) => atomicWriteJson(file, state, ctx.logger, prefix, { force, maxBytes }) })`——`schedule()` 变更后调度（窗口内重复变更自动合并）、`drain()` 是确定性就绪信号（测试/就绪判断用它，别 sleep 猜时间）、`flush()` 在 teardown 立即强写（`force` 跳过防抖/节流窗口）。

必须满足：

- 每次变更防抖（500ms）+ 最小间隔（≥1s）合并批量写，节奏由**调度器**保证（护栏只是兜底；调度器 `minIntervalMs` 应与护栏窗口一致，默认均 1000ms）。
- 单次序列化字节有上限（`atomicWriteJson` 默认 1MB；状态更大时显式放宽，并在 issue 的「资源影响」栏写清「状态字节上界公式 + 实测值」）。
- 状态自身有上界（条目**且**字节）：容器用 `boundedMap` / `boundList`，不要裸 `Record`/`Map`/数组。
- 被护栏拦截**不静默**：`atomicWriteJson` 默认 warn + 计数（`atomicWriteStats()`），调度器对 `false` 返回自动重排。
- 测试不得用固定 sleep 等落盘（用 `drain()`，见 [踩坑目录](../踩坑/README.md)「测试随机失败：固定 sleep 与并行撞锁」）；高频增量场景即使状态小也应评估切换事件流型。

### 2.3 内存有界容器

用 `dsh-shared` 的 `boundedMap({ maxSize })`（LRU，默认；`policy: 'fifo'` 可选）与 `boundList({ maxSize })`（FIFO，列表顺序即插入序）；淘汰计数经 `evicted` / `stats()` / `onEvict` 观测。

- 上限**显式**（容器默认值只是兜底，不是设计值）；issue 的「资源影响」栏写「上限 × 单条大小 = 内存上界」。
- 不静默丢数据；不拿有界容器存**审计明细**（淘汰即丢数据 → 应落 `jsonlAppender`）；数组不做 LRU。

### 2.4 自监测降级（资源看门狗）

**不要自己实现**：用 `dsh-shared` 的 `createResourceGuard`（`lib/resource-guard.js` + `lib/resource-rules.js`；采样 → 纯函数判定 → 连续确认 → 降级/恢复，ring buffer 有界、`stats()` 可观测、`now` 可注入）。宿主只提供采样源与降级动作，示例见 `plugins/dsh-my-observability/src/resource-monitor.ts`。

```
周期采样（15s：cpuUsage / memoryUsage / 文件字节）→ ring buffer（最近 60 个）→ 纯函数判定（写速率 / 文件大小 / CPU / 内存）
  任一关键阈值连续 ≥3 次超限 → 降级：L1 提高持久化节流间隔（写盘次数减少，字节不变）
                                   L2 停止事件落盘（内存有界，恢复时全量快照补齐）
                                   L3 事件降采样（只留状态/流事件）＋记日志＋面板告警
  降级中连续 ≥3 次正常 → 恢复：内存状态全量快照落盘（补齐窗口）＋恢复增量
```

降级设计要求：判定与动作分离（判定为**纯函数**可单测，动作由宿主注入回调）；采样开销可控（<0.01% CPU）；降级状态下内存/文件仍有界；恢复必须全量快照一次（内存是真相）；阈值可配置覆盖（`config.resourceLimits`），但监控不可关。

## 3. 五维资源评审表（开发前逐行填写）

| 维度           | 评估公式                                    | 建议上限                                   |
| -------------- | ------------------------------------------- | ------------------------------------------ |
| 磁盘 IO 写入量 | 单次写字节 × 频率 × 运行时长                | **< 10 MB/小时**                           |
| 写放大倍数     | (单次写字节 × 频率) ÷ (真实增量字节 × 频率) | **≤ 1.5**                                  |
| CPU            | 最热路径复杂度 × 触发频率                   | **< 5% 单核** 持续                         |
| 内存           | 常驻结构大小 × 条目上限 × 1.5               | **< 200MB**，峰值不随运行时长线性增长      |
| 网络           | SSE/心跳/流字节 × 频率                      | **< 5 MB/分钟**                            |
| 磁盘存量       | 文件大小上界 + 轮转/compact 策略            | **< 500MB** 且大小有界（不能只设条目上限） |

超出上限必须写明理由并让用户确认。方法论见 [resource-budget-review](../../skills/resource-budget-review/SKILL.md)。

## 4. 写放大判定（最常踩的坑）

1. **全量序列化 + 高频防抖**：`debounce → writeFile(tmp, JSON.stringify(整个状态))`，写放大 ≈ 数百~数千倍。**正解**：增量 append + 周期 compact。
2. **条目上限 ≠ 字节上限**：只限"数量"不限"每次重写的字节数"和"写入频率"。
3. **O(n) 计数/查询在热路径**：用维护计数器/索引，别每事件全量遍历或拷贝。
4. **原子写原语错配**：`writeFile(tmp)+rename` 是"正确性第一"的快照原语，只用于低频全量快照。
5. **降级缺失**：监控到超限只告警不动作 → 降级动作 + 恢复路径必须预设计。

## 5. 三遍校验（设计 → 开发 → 运行）

| 阶段   | 动作                                                                                                              | 证据                             |
| ------ | ----------------------------------------------------------------------------------------------------------------- | -------------------------------- |
| 设计期 | 按 §3 估算并填「资源影响」（IO 量级 / 内存上界 / CPU 影响）+ 选定 §2 持久化模式 + 设计降级路径                    | issue 的「资源影响」栏           |
| 开发期 | **写放大复现测试**（高频 N 事件落盘字节 ≤ 事件本体 × 系数，如 1.6）+ 复杂度上限断言 + **降级触发/恢复测试**       | 单测断言（先看它在旧实现上失败） |
| 运行期 | 功能级验证清单加「**资源曲线平稳**」：观察 ≥30 分钟，写入 <100MB、CPU <10%、内存无线性增长 + CI 资源冒烟 job 通过 | 验证清单勾选 + 采样数据          |

## 6. 提交前快速检查清单

- [ ] 持久化原语选型正确（事件流 → `jsonlAppender`；状态 → `createWriteScheduler` + `atomicWriteJson`），且复用 `dsh-shared` 现成原语而非自写样板？
- [ ] 有界容器上限显式、淘汰计数可观测（不是裸 `Record`/数组）？内存峰值有上界证明（不随运行时间/事件数线性增长）？
- [ ] 写放大倍数给出数字（≤1.5）且有复现测试？单次序列化字节上限显式（不是 Infinity）？文件大小有字节上限（compact/轮转）？
- [ ] 高频路径无 O(n)/O(n²)？测试用 `drain()` 等确定性就绪信号等落盘（不是固定 sleep）？
- [ ] 有自监测降级路径（采样 → 判定 → 动作 → 恢复）？issue 的「资源影响」栏已填、验证清单勾了「资源曲线平稳」、CI 资源冒烟 job 通过？
