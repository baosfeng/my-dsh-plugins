# 插件插件资源安全规范

> **适用范围**：本仓库所有 DSH 插件（server 端持续运行逻辑：事件监听 / 持久化 / 轮询 / 流处理 / 后台任务）。
> 开发或修改此类逻辑前，先读 [resource-budget-review](../../skills/resource-budget-review/SKILL.md) 与本文档，评审完五个资源维度（IO/CPU/内存/网络/磁盘存量）后才算完成。
>
> **触发背景**：issue #126——dsh-my-observability 事件审计在生产实例引发高 CPU（423%）/内存峰值 4.7G/约 300GB 磁盘写入事故；外部同类案例：DSH 官方 `session_projcache.json` 在长会话中全量重写导致 ~100MB/s 磁盘写入（见 [踩坑记录](../踩坑/README.md)）。

## 1. 核心原则

1. **正确 ≠ 便宜**：功能测试通过只证明"它工作"，不证明"它便宜"。资源成本（写放大/CPU/内存）必须**显式评估并用数字守住**，最好有自动化断言。
2. **先选对持久化原语，再谈优化**：原语错配是写放大事故的根源（#126：事件流用全量快照原语）。
3. **监控是降级的先决条件，降级是监控的目的**：只告警不动作 = 事故仍要等人手动介入（#126 复盘缺口 3）。
4. **降级必须可恢复、有界**：降级动作要保证内存/文件有界，且资源回落后自动恢复，不丢失降级前数据。

## 2. 高频写路径分级与模式选型

按"写的内容形态"给持久化路径分级，选型如下：

| 形态           | 特征                         | 持久化原语                                    | 代表                                                      |
| -------------- | ---------------------------- | --------------------------------------------- | --------------------------------------------------------- |
| **事件流型**   | 高频追加、每条独立、总量增长 | **增量 append（jsonl）+ 周期 compact**        | observability 审计（`lib/store.js` + `store-persist.js`） |
| **状态快照型** | 低频全量、整体替换、数据汇总 | **原子写 tmp+rename + 护栏**（节流/字节上限） | context 统计（`atomicWriteJson`）、file-activity LRU      |
| **计数器型**   | O(1) 更新、无跨会话累积结构  | 内存维护 + 低频快照（>10s 节流）              | token 计数（若做成本地持久化）                            |
| **无状态型**   | 不需要持久化                 | 不落盘，纯内存（注意内存上限）                | 审计视图过滤等纯函数                                      |

> **判定口诀**：**事件流型禁止用全量快照原语**（写放大 = 状态大小/事件大小，数百~数千倍，正是 #126 根因）；状态快照型禁止高频触发（防抖 + 节流窗口 + 字节上限）。

### 2.1 事件流型（最高风险）模板

```js
// 复用 dsh-shared 的 jsonlAppender（plugins/dsh-shared/lib/jsonl.js）
import { jsonlAppender } from 'dsh-shared'

const store = jsonlAppender(file, {
  flushMs: 500, // 防抖批量 append（写放大 ≤ 1 + 小系数）
  compactLines: 5000, // 行数阈值触发宿主 compact（文件字节有界）
  logger: ctx.logger,
  onCompact: () => {
    store.snapshot(renderAllLines()) // 宿主用内存全量生成行，原子重写
  },
})

store.append(event) // 高频事件只入队
// 卸载时：store.dispose() 冲刷挂起数据
```

**必须满足**：

- 落盘字节 ≈ 事件本体字节（增量 append，禁止整桶全量重写）；
- 有**字节上限**（compact/轮转），不是只有条目上限；
- 加载解析容错（坏行跳过不崩溃）；
- 内存有上界（条目上限 + 全局上限，FIFO 淘汰）。

### 2.2 状态快照型模板

```js
// 复用 dsh-shared 的 atomicWriteJson（plugins/dsh-shared/lib/persist.js）
import { atomicWriteJson } from 'dsh-shared'

// 必须显式传护栏参数——否则 maxBytes 默认 Infinity（无字节护栏）！
atomicWriteJson(file, state, logger, prefix, {
  minIntervalMs: 5000, // 节流：同文件 <5s 内第二次写被拦
  maxBytes: 512 * 1024, // 单次写上限：512KB 拒绝
})
```

**必须满足**：

- 每次变更防抖（500ms）+ 节流窗口（≥1s）合并批量写；
- 单次序列化字节有上限（超出降级或拒绝）；
- 状态自身有上界（条目上限 **且** 字节上限）；如 file-activity 的 `counts` 字典需补上限（见调研报告整改项）；
- 高频增量场景即使状态小，也应评估是否切换事件流型。

### 2.3 自监测降级模板（资源看门狗）

> #126 复盘缺口 3「无降级机制」的直接对策。observability v0.1.5 起内置（`lib/resource-monitor.js` + `resource-rules.js`），新插件照此模式实现。

```
周期采样（15s：process.cpuUsage / process.memoryUsage / 文件字节）
   │
   ▼
样本进入 ring buffer（保留最近 60 个）
   │
   ▼
纯函数判定（thresholds: write-rate / file-size / cpu / memory）
   │
   ├─ 任一关键阈值连续 ≥3 次超限 → 进入降级（onDegrade 回调）
   │     降级动作（按影响从小到大选择，可组合）：
   │       L1 提高持久化节流间隔（写盘次数减少，字节不变）
   │       L2 停止事件落盘（内存有界，恢复时全量快照补齐）
   │       L3 事件降采样（只保留状态/流事件，丢弃明细）
   │     动作同时记日志 + 面板告警
   │
   └─ 降级中连续 ≥3 次正常 → 恢复（onRecover 回调）
         恢复动作：内存状态全量快照落盘（补齐降级窗口）+ 恢复增量
```

**降级设计要求**：

- 判定与动作分离：判定为**纯函数**（可单测，如 `decideDegrade`），动作由宿主注入回调；
- 采样自身开销可控（15s 一次，<0.01% CPU）；
- 降级状态下内存/文件必须仍有界（FIFO/上限不因降级失效）；
- 恢复必须全量快照一次（内存是真相），避免丢行或重复；
- 配置可覆盖阈值（`config.resourceLimits`），监控不可关。

## 3. 五维资源评审表（开发前逐行填写）

| 维度               | 评估公式                                              | 建议上限（DSH 插件场景）                | 不合格的典型表现                          |
| ------------------ | ----------------------------------------------------- | --------------------------------------- | ----------------------------------------- |
| 磁盘 IO 写入量     | 单次写字节 × 写入频率 × 预计运行时长                  | **< 10 MB/小时**（≈240MB/天）           | "每次落盘全量重写整个状态文件"            |
| 磁盘 IO 写放大倍数 | (单次写字节 × 频率) ÷ (真实增量字节 × 频率)           | **≤ 1.5**（≈增量写）                    | ≥ 几百倍（全量序列化用于高频增量场景）    |
| CPU                | 最热路径复杂度 × 触发频率（序列化对象大小 × 次数/秒） | **< 5% 单核** 持续                      | 每次事件 O(n) 遍历 / 每事件全量 stringify |
| 内存               | 常驻结构大小 × 条目上限 × 1.5                         | **< 200MB**，且峰值不随运行时长线性增长 | 峰值持续上升 = 泄漏；2.4G→3.8G 即警报     |
| 网络               | SSE/心跳/LLM 流字节 × 频率                            | **< 5 MB/分钟**                         | 每事件全量回传 / 无节流轮询               |
| 磁盘存量           | 文件大小上界 + 轮转/compact 策略                      | **< 500MB** 且大小有界                  | 只设"条目上限"不设"字节上限"              |

> 对应 [resource-budget-review](../../skills/resource-budget-review/SKILL.md) 的五维表。超出上限必须写明理由并让用户确认。

## 4. 写放大判定（最常踩的坑）

1. **全量序列化 + 高频防抖**（#126 事故模式）：`debounce(500ms) → writeFile(tmp, JSON.stringify(整个状态))`。事件流持续时写放大 = 状态大小/事件大小 ≈ 数百~数千倍。
   **正解**：增量 append（jsonl/追加日志）+ 周期 compact（阈值触发原子快照）。
2. **条目上限 ≠ 字节上限**：2000 条/会话只限"数量"，不限"每次重写的字节数"和"写入频率"。字节上限必须显式设计。
3. **O(n) 计数/查询在热路径**：每事件全量遍历计数、每事件全量拷贝。用维护计数器/索引。
4. **原子写原语错配**：`writeFile(tmp)+rename` 是"正确性第一"的快照原语，只用于低频全量快照；高频增量必须用 append。
5. **降级缺失**：监控到超限只告警不动作，事故仍要人工介入。降级动作（节流/停写/采样）+ 恢复路径必须预设计。

## 5. 三遍校验（设计 → 开发 → 运行）

| 阶段   | 动作                                                                                                                | 证据                             |
| ------ | ------------------------------------------------------------------------------------------------------------------- | -------------------------------- |
| 设计期 | 按 §3 估算并填"资源影响"（写 IO 量级/内存上界/CPU 影响）+ 选定 §2 持久化模式 + 设计降级路径                         | 需求清单「资源影响」栏           |
| 开发期 | **写放大复现测试**：高频 N 事件落盘字节 ≤ 事件本体字节 × 系数（如 1.6）；复杂度/循环上限断言；**降级触发/恢复测试** | 单测断言（先看它在旧实现上失败） |
| 运行期 | 功能级验证清单加「**资源曲线平稳**」：观察 ≥30 分钟，写入 <100MB、CPU <10%、内存无线性增长 + CI 资源冒烟 job 通过   | 验证清单勾选 + 采样数据          |

## 6. 提交前快速检查清单

- [ ] 持久化原语选型正确（事件流→append；状态→原子写+护栏）？
- [ ] 写放大倍数给出数字（≤1.5）？有写放大复现测试？
- [ ] 单次序列化字节上限显式设置（不是 Infinity）？
- [ ] 内存峰值有上界证明（不随运行时间/事件数线性增长）？
- [ ] 文件大小有字节上限（compact/轮转），不是只有条目上限？
- [ ] 高频路径无 O(n)/O(n²)？有维护计数器？
- [ ] 有自监测降级路径（采样→判定→动作→恢复）？
- [ ] 需求清单「资源影响」栏已填？验证清单勾了「资源曲线平稳」？
- [ ] CI 资源冒烟 job 通过（见 `资源占用防护 CI`）？
