# 构建与测试

> ⚠️ **何时阅读：** 构建/测试/提交前必读。

## 测试执行与修复

### 需求回归（强制要求）

> **任何插件的新功能开发或修改，都必须对照该插件的需求清单做回归检查，确保不破坏既有功能。**

- 每个插件文档目录下维护 **需求清单**（如 `docs/文件活动追踪/需求清单.md`），逐条列出用户明确的需求（含持久化、会话隔离、重启恢复等易被连带破坏的点）。
- **开发前**：读取需求清单，列出本次改动涉及/可能影响的需求条目。
- **开发后**：对照清单逐条验证（跑测试 + 手动验证受影响条目），确认无回归后才能提交。
- **新增功能**：必须在需求清单中补充对应条目，并添加测试用例覆盖（禁止只改代码不补测试）。
- **易碎需求**（重启恢复、会话隔离、持久化、数据不丢失等）默认需要专门测试断言 + 手动验证，不得只依赖"看起来没变"。
- **验证后清理环境（强制）**：涉及真实进程/浏览器/独立端口的验证（如 3081 隔离实例）完成后，必须清理：停掉后台实例、删除临时验证目录（`/tmp/dsh-<port>`）、关闭验证用浏览器（`browser_close` + 专用 CDP Chrome）、确认端口释放、`job_list` 无 running 残留。**多插件并行开发时，验证残留会互相干扰**，每个插件的验证环境用完即清。

### 发布后本地更新与验证（强制要求）

> **发版完成 ≠ 交付完成。发版（tag/Release）后必须把本地生产实例更新到位并亲自验证，不能"发完不管"。**

- 本仓库插件在本机以 `link:` 安装（指向仓库源码），**代码更新即时生效，但进程不重启不加载**——发版后必须重启本机 `dsh web` 让新版本/新插件生效；
- 重启后必须亲自验证（同 [真实环境全流程验证](#真实环境全流程验证强制要求) 的冒烟标准）：
  - 配置组合无重复（`dsh --profile web --dump-config`）；
  - 实例 HTTP 200、启动日志无 error；
  - 变更插件的 API 冒烟 200（如 `/my-skill-manager/api/list`、`/my-plugin-manager/api/installed`）；
  - 新页签/新入口在 GUI 可见（设置页/侧边栏）。
- 新增插件部署后同样必须重启 + 验证（不验证 = 未完成）；
- ⚠️ 重启会中断当前运行中的 DSH 实例（含正在进行的会话）——确认时机后执行，验证完成后向用户汇报。

### 测试执行要求

> **提交前必须运行全部测试，修复所有失败的测试用例，确保全部通过。**

- 每次提交前都应当运行项目对应的测试命令
- 如果存在测试失败，必须修复后才能提交
- CI（`.github/workflows/ci.yml`）会遍历 `plugins/*/` 执行 `node --check` 语法检查 + `npm test` 冒烟测试

### 真实环境全流程验证（强制要求）

> **每次插件开发完毕（含新建插件、功能修改、修复、依赖变更），提交前必须执行完整真实验证。**

只跑单元测试/独立全新实例**不够**：`duplicate loader entry id` 这类配置组合炸弹只会在「生产 profile 的真实配置组合」里出现（bundle 自动插行 + profile 手动 patch 行叠加），全新实例永远测不出。必须用**配置副本模拟**复刻生产配置组合做全流程验证：

```bash
# 一键全流程验证（配置组合检查 + 真实启动 + API 冒烟 + 自动清理）
node scripts/verify-real-profile.mjs --addons plugins/<新插件目录> [--addons ...] [--api-path /<插件>/api/xxx]

# 只做配置组合检查（不启动实例，快）
node scripts/verify-real-profile.mjs --skip
```

验证脚本覆盖（任一失败即退出码 1）：

| 环节          | 内容                                                                                                              |
| ------------- | ----------------------------------------------------------------------------------------------------------------- |
| 1. 复刻配置层 | 复制生产 profile 的 package.json / cordis.yml / cordis.patch.yml 到临时 DSH_HOME，node_modules 全量软链（零拷贝） |
| 2. 模拟安装   | `--addons` 插件写入临时 profile 的 bundles + dependencies（完全复刻 `dsh plugin add` 落盘效果）                   |
| 3. 配置组合   | `dsh --profile <p> --dump-config` 校验插件行 id 全局唯一（duplicate loader entry 检测）+ addons 已入组合          |
| 4. 真实启动   | 独立端口启动实例（插件树加载 + apply + 路由注册）                                                                 |
| 5. 日志与健康 | HTTP 200 + 启动日志无 error / duplicate / failed to apply                                                         |
| 6. API 冒烟   | 对每个 `--api-path` 做 GET，200 即 server 端生效                                                                  |
| 7. 自动清理   | 停实例（等进程退出）+ 删临时目录，零残留                                                                          |

> **发版强制集成（issue #39 + #67）**：`scripts/release.mjs` 发版流程（含 dry-run）自动执行本脚本（`--addons plugins/<名>`），失败即阻断发版——发版前必须经历真实环境验证。CI（GitHub Actions）无生产 profile 自动跳过；本地可用 `--skip-real-verify` 显式跳过，但 **issue #67 起必须带 `--skip-reason "<理由>"` 显式记录原因，无理由直接 exit 1**。

> **发版前功能级验证门禁（issue #67，强制）**：仅启动级验证不够——release.mjs 3c 步骤在自动验证通过后会生成「发版前功能级验证清单」（`verification/<插件>-<版本>.md`，自动项自动勾选），并**校验功能级项（核心功能走通 / 易碎场景 / client UI / 插件联动 / 环境清理）全部勾选**，未全勾选即阻断发版。功能级项须在隔离实例 + 真实浏览器中验证后勾选（配合盲测子 agent，见下）。清单文件随发版 commit 一并提交归档。非 bundle 形态插件（agent preset，如 dsh-plugin-dev-mode）按自身安装方式验证并手写同格式清单（注明验证方式）。流程细节见 `verifying-dsh-plugins` skill「发版前功能级验证」章节。
>
> 📌 **清单版本约定**：release.mjs 在 3c 前先执行 `--bump`，清单文件名版本 = **即将发版的版本**（bump 后的 next，非当前 package.json 版本）。手动预验证时 `--checklist`/`--version` 必须用同一版本（如 `--bump patch` 则用当前版本 +1），否则 release 3c 生成不同文件名的清单，已勾选的验证留痕不会被读取（触发阻断，需对齐文件名后重跑）。

**盲测（可选但推荐）**：涉及新功能/新插件时，除脚本验证外，用**盲测子 agent**（不了解实现的独立上下文）在验证实例上以真实用户视角操作 GUI，按「功能可用性 → 易碎场景（刷新/重启保持）→ 错误路径 → 体验」验收并输出问题分级清单。

> ⚠️ **验证后清理环境（强制）**：验证完成后必须停掉后台实例、删除临时目录（脚本自动完成；手动搭建时按下方「验证后清理」执行）。多插件并行开发时，验证残留会互相干扰。

## 本地一键校验（verify-local）

> **提交/push 前一条命令复现 CI 全部门禁**（`.github/workflows/ci.yml` 的 audit / test / mutation / quality / resource-smoke 5 个 job），本地全部通过后远程 CI 一片绿。
>
> 两种模式：**`full` 全量**（CI 等价，`npm run verify` / `--full`）与 **`fast` 快速通道**（`--fast`，`.husky/pre-push` 默认用这个）——fast 只按本次推送的变更裁剪插件测试，独立性检查照跑只是并发；**无变更证据时安全退化为全量**。

### 命令

```bash
npm run verify                # 全量（= node scripts/verify-local.mjs，等价 CI 门禁，不含 audit/mutation）
npm run verify:full           # 同上（显式全量入口）
npm run verify:fast           # 快速通道（pre-push 用的同一入口）
node scripts/verify-local.mjs --fast --base origin/main  # 指定范围比较基准
node scripts/verify-local.mjs --full          # 强制全量（覆盖 --fast）
node scripts/verify-local.mjs --audit          # 额外执行 npm audit（默认跳过；需联网，钉官方 registry）
HTTPS_PROXY=http://127.0.0.1:7890 npm run verify --audit   # 本机需要代理时这样跑（见「依赖漏洞审计」）
node scripts/verify-local.mjs --mutation       # 额外执行 stryker 变异测试（默认跳过，约 20s）
node scripts/verify-local.mjs --only knip      # 只跑单项（开发中快速迭代；可重复：--only a --only b）
node scripts/verify-local.mjs --list           # 列出全部检查项 id
node scripts/verify-local.mjs --plugin dsh-my-guard   # 只跑该插件的 --check + npm test（可重复）
```

- **pre-push 自动执行快速通道**：`.husky/pre-push` 跑 `node scripts/verify-local.mjs --fast`，失败阻止 push；脚本开头必跑的一段是 `unset GIT_DIR GIT_WORK_TREE ...`（issue #127：不清会让各插件测试里创建临时 git 仓库时被 `GIT_DIR` 劫持而全挂）。`pre-commit` 仍由 lint-staged 负责增量 lint/格式化。
- **pre-commit 只做增量**：lint-staged 对暂存文件跑 `eslint --fix` + `prettier --write`，耗时与暂存文件数成正比（不随仓库规模增长）。
- **pre-commit 的 index.lock 竞争兜底**（`.husky/pre-commit`，实测事故）：git 运行 hook 时**不持有** `index.lock`，若此刻另一个进程正在写 index（并行 agent / 编辑器 / 另一条 `git add`·`stash`·`reset`），lint-staged 的 `git stash create` 会以 `error: could not write index` 失败，被它统一报成 `Failed to back up original state!` 并跳过全部任务 → **提交被挡，但零数据丢失**。**指纹**：恢复提示打印的是字面量 `<git-hash>`（说明 `backupHash` 从未赋值）且 `git stash list` 为空。**与 rename 无关**——用含 3 个真实 `git mv` 的暂存集精确重建稳定通过，触发因素只是时间窗口，所以表现为偶发。
  hook 现在的行为：命中该特征 → 等 1s **自动重试一次**（锁竞争是瞬时的，且此刻 lint-staged 尚未改动任何文件，重试安全）→ 仍失败则**降级**为对暂存文件跑 `eslint --fix-dry-run` + `prettier --check`，合格就放行并说明原因。降级刻意**只读**：正常路径靠 stash 才能安全地「改完再重新 stage」，该前提已失效时写盘会污染部分暂存状态。
- **失败语义**：任一检查失败 exit 1，且**继续跑完其余检查**，最后汇总所有失败项，方便一次修完；全部通过 exit 0。
- **`--fast` 每次都会打印它实际跑了什么**（基准 ref、变更文件数、受影响插件清单、跳过项及原因），并提示 `npm run verify` 可全量复现。
- **与 scripts/test-all.sh 的关系**：test 检查项复用其遍历逻辑（`plugins/*/` 有 package.json 的目录，逐个 `node --check` + `npm test`），但不在脚本里直接调用它——test-all.sh 用 `set -e` 遇到首个失败即中断，无法"跑完全部并汇总"，也不支持 `--plugin` 过滤，故在 `scripts/verify-local.mjs` 内联同逻辑。

### `--fast` 的范围裁剪规则（影响面）

比较基准：`@{upstream}` → 无 upstream 时回退 `origin/main` / `origin/master`（用 `git diff <base>...HEAD`，即"远程没有的提交"）。

| 变更路径                                                                    | 插件测试范围                                                                 |
| --------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| `plugins/<name>/**`（低扇入）                                               | 只跑 `<name>` + 其依赖方（package.json 声明 + 源码 `import` 两路取证）       |
| 高扇入共享库（`plugins/dsh-shared/**`，13 个插件依赖）                      | **安全退化 → 全部插件**（逐个跑依赖方 ≈ 全量，且不留"漏掉间接依赖方"的口子） |
| `docs/**`、`skills/**`、`*.md`                                              | **不跑插件测试**，且跳过一切只针对源码的检查（lint/typecheck/knip/jscpd/…）  |
| `scripts/**`、根工具链文件（`package.json`/`knip.json`/`tsconfig.json` 等） | **安全退化 → 全部插件**（无法安全推断影响面）                                |
| 无 upstream / 无 `origin/main` / `git diff` 失败 / `--base` 不可解析        | **安全退化 → 全部插件**，并在输出里给出原因                                  |

- **对比语义**：范围只看 `base...HEAD`（**已提交**内容），未提交的工作区改动不参与裁剪——这正是 push 实际传输的内容。用 `-c core.quotepath=false` 读变更列表，中文路径（本仓库 docs/ 大量中文名）才能正确匹配前缀规则。
- **只跑 3 项也需要理由**：纯文档推送只跑 `format`（本次变更文件）+ `docs`（文档一致性）+ `links`（文档引用完整性），其余 9 项都被打印为"按范围跳过 + 原因"。
- **独立性检查恒跑（只是并发）**：typecheck / lint / format / knip / jscpd / depcruise / test-scripts / docs / links。
- **带证据才跳过的项**：
  - `ts-size`：本次变更不含 `.ts`/`.tsx` 时跳过（该门禁只统计 TS 源码规模，基线未动不可能失败）；
  - `resource-smoke`：变更未触及 `dsh-my-observability` / `dsh-shared` 时跳过（该门禁只覆盖这两个插件的事件存储增量模型）；
  - `format`：`--fast` 下只 check 本次变更文件（变更集为空时退化为全仓库检查）。
- **并发与顺序**：检查项 4 路并发；插件测试 3 路并发（各插件测试相互隔离：独立 node 进程 + 临时 `DSH_HOME` + port 0，无固定端口）。`depcruise` 必须等插件测试结束再跑（测试会创建/清理各插件 `coverage/` 目录，扫到半截会 ENOENT）；`dsh-my-guard` 独占运行（其黑名单扫描测试真去 npm registry 解析包名，含 5s 超时用例，并发下曾误报超时）。同一仓库另有进程在跑同一插件 vitest 时会争用 coverage 目录（见 docs/踩坑/多agent并行测试资源冲突.md），可用 `VERIFY_CONCURRENCY=1..8` 覆盖插件测试并发度（怀疑冲突时设 1 串行）；失败汇总会自动打印这条排查提示。

### 性能画像（本机实测，M 系列 Mac）

实测命令：隔离克隆 + 真实钩子路径 `bash -c 'cd <clone> && .husky/pre-push'`（不是估算，也不是空跑）。

| 场景                                  | 改前（旧脚本，全串行全量） | 改后（fast，默认） |
| ------------------------------------- | -------------------------- | ------------------ |
| 只改 1 个插件源码（dsh-my-notify）    | 114s                       | **11s**（约 10×）  |
| 只改 `docs/**`                        | 114s                       | **0.3s**           |
| 无变更证据（基准不可解析 → 退化全量） | 115s                       | 43s（约 2.7×）     |
| 全量入口 `npm run verify`             | 115s                       | 42s（约 2.7×）     |

- 达标判断：日常场景（改 1 个插件 / 改文档）从"数分钟"降到 **11s / 0.3s**，落在"几十秒内"目标区间。
- 全量退化路径 43s（原本 115s）的收益来自**并发 + `depcruise` 后置**，不来自裁剪——此时 19 个插件测试一个不少。
- 逐项耗时画像（改前串行，同一台机器）：19 个插件 `npm test` 合计 **97s**（最慢 `dsh-file-activity` 23s、`dsh-my-observability` 22s、`dsh-my-notify` 9s、`dsh-task-reliability`/`dsh-my-guard`/`dsh-my-guardian` 各 7-8s），其余 10 项检查合计仅 **~18s**（最慢 `resource-smoke` 6s、`format` 5s，其余 ≤2s）——**大头 100% 在插件测试**，所以裁剪 + 并发都盯着它。
- 本机 `npm run verify`/`--full` 并行度：检查项 2 路、插件测试 3 路。

### 依赖漏洞审计（issue #199）

> **改依赖（升级/新增/改 overrides）后，`npm audit` + `npm ci` 是必跑项**，且 audit 必须走**官方 registry**。

#### 为什么必须钉官方 registry

`npm audit` 依赖 registry 的 advisories 端点（`POST /-/npm/v1/security/advisories/bulk`），
而 **npmmirror 等镜像没有实现它**（`404 [NOT_IMPLEMENTED] /-/npm/v1/security/*`）——本地 audit 直接不可用。
更坑的是两个**反直觉**行为（npm 11 实测，完整复盘见 [踩坑/npm-audit 在镜像源下静默失效](../踩坑/npm-audit在镜像源下静默失效.md)）：

1. **`--registry` 会被重写回镜像**：npm 的 `replace-registry-host` 默认值 `npmjs` 会把 `registry.npmjs.org`
   的地址换成**当前配置的 registry**。所以「加个 `--registry` 就完事」是错的，必须同时 `replace_registry_host=never`；
2. **只看退出码分不清「没查成」与「没问题」**：镜像下 audit 也会正常退出并打印提示。
   判定必须看输出里**是否真的有结构化报告**。

#### 本地怎么跑

```bash
# 一条命令（verify-local 的 audit 项已内置官方 registry + 禁止重写 + moderate 门槛）
HTTPS_PROXY=http://127.0.0.1:7890 npm run verify --audit   # 不需要代理时去掉 HTTPS_PROXY
node scripts/verify-local.mjs --only audit                  # 只跑 audit（秒级）

# 直接调 npm（本机 registry 是镜像时，这样也能真正查到官方数据）
HTTPS_PROXY=http://127.0.0.1:7890 \
  npm_config_registry=https://registry.npmjs.org \
  npm_config_replace_registry_host=never \
  npm audit --audit-level=moderate
```

- 钉官方 registry 由 `scripts/lib/npm-audit.mjs` 统一提供（CI 与本地共用同一套判定，避免两处各写一份再跑偏）；
- audit 项**未真正执行**（端点不支持/网络不可达）时判**失败并打印原因**，不会静默放过；
- 有漏洞时输出人类可读清单（受影响版本范围 + 公告链接 + 修复建议 + 传入路径），失败退出码可用于门禁。

#### CI 门禁

独立 audit job（`.github/workflows/ci.yml`）：官方 registry + `npm_config_replace_registry_host=never`

- **`--audit-level=moderate`**（moderate 及以上即阻断）。

> **为什么是 moderate 而不是 high**：原设置 `--audit-level=high` 会**放行 moderate**——issue #199 的 2 条
> `qs` moderate 公告因此在 CI 里「只打印、不阻断」，长期沉积无人处理。npm 的语义是：未达 `--audit-level`
> 的漏洞**不影响退出码**，只打印。低危（low/info）仍不阻断，避免上游新公告噪声。

#### 改依赖时的检查清单

```bash
npm audit   # ① 官方 registry，0 vulnerabilities（命令见上）
npm ci      # ② lockfile 完整性 —— CI 用 npm ci，锁文件不自洽会直接红
npm run verify   # ③ 全量门禁（含打包/类型/文档一致性；audit 项需显式 --audit）
npm audit fix    # ④ 能非破坏性直接修就修（#199 的 qs 6.15.3 → 6.16.0 只改了 3 行 lockfile）
```

#### 排查命令（怀疑「没查到」时按顺序试）

```bash
npm config get registry                  # 本机指向镜像？
npm audit --registry=https://registry.npmmirror.com   # 复现「端点未实现」
npm audit --registry=https://registry.npmjs.org       # 反直觉：仍然打到镜像（被重写）
npm_config_replace_registry_host=never npm audit --registry=https://registry.npmjs.org   # 这次才是官方源

# Dependabot 面板默认只显示 open —— 被 auto_dismissed/fixed 的告警要显式查 closed
ghops alerts <owner/repo> --state closed --kind dependabot
```

### 已知限制

- **audit 默认跳过**：本地需要联网；CI 的 audit job 用官方 registry 强制执行 `npm audit --audit-level=moderate`（moderate 及以上即阻断）。本地用 `--audit`（需要代理时按「依赖漏洞审计」一节加 `HTTPS_PROXY`），或直接依赖 CI 门禁。
- **mutation 默认跳过**：stryker 本地约 20s，push 前全量跑太重；CI mutation job 独立并行强制执行。需要时 `--mutation` 开启。
- **无"仅 CI 执行"的检查**：`node scripts/check-docs.mjs` 为纯本地文件一致性检查（读根 README / AGENTS.md / docs/ 索引与模块文档 / 插件 package.json），不依赖网络，本地可完整复现。
- **fast 裁剪的残余风险（诚实评估）**：以下情形 fast 可能漏检，靠 CI 兜底——(1) 某插件测试断言的其实是**另一个未改动插件**的行为（当前仓库无此形态：插件间无源码级交叉 import，依赖关系由 package.json + 源码 import 两路取证）；(2) 插件运行时读取了**未改动插件的资源文件**（如跨插件的 JSON 配置）——不在这两路取证范围内，本仓库当前无此形态；(3) `resource-smoke` 覆盖的存储实现被**间接调用方**改动（直接改 `dsh-my-observability/**` 或 `dsh-shared/**` 会命中，改其调用方不会）；(4) 只改文档确实影响 `check-docs.mjs` 的断言对象（README 插件表/版本行等）——docs 检查在 fast 恒跑，已覆盖；(5) 并发下 `dsh-my-guard` 那个 5s 超时的联网用例理论上仍可能误报超时（已独占运行降低概率；失败时脚本会打印 `VERIFY_CONCURRENCY=1` 复测提示）。**发版、改根工具链、改 dsh-shared、或对结果有疑问时，跑 `npm run verify` 全量。**
- **test 范围略严于 CI**：本地遍历 `plugins/*/` 全部 19 个含 package.json 的目录（含 dsh-shared 共享工具包），CI test matrix 不含 dsh-shared——本地多测一个库，更严格。

## 常用测试命令

- 单个插件冒烟测试：`cd plugins/<插件名> && npm test`（即 `node test/host-smoke.mjs`）
- 语法检查：`node --check plugins/<插件名>/lib/index.js` 与 `lib/client.js`
- 遍历全部插件：`for d in plugins/*/; do [ -f "$d/package.json" ] && (cd "$d" && npm test); done`
- 依赖浏览器/真实 GUI 的测试（`test/e2e-cdp.mjs`）留本机手动运行；`test/client-render.mjs` 为零依赖渲染测试（自写 react stub），随 `npm test` 在 CI 运行

> **精简测试输出：** 冒烟测试为纯 Node 脚本，输出即摘要；无需额外静默参数。

## 单元测试与集成测试

### 单元测试（冒烟测试）

- 位于 `plugins/<name>/test/`（如 `host-smoke.mjs`，mock ctx / webServer / betterSidebar）
- **每次提交前必须自动运行并全部通过**
- 如果存在失败的测试，必须先修复后才能提交
- 运行命令：`cd plugins/<name> && npm test`

### 集成测试（手动）

- 涉及真实 DSH 进程/浏览器的测试（`e2e-cdp.mjs` 等）**必须人工指定触发**，不得随 CI 自动运行
- 由开发者在确认环境就绪后手动执行

## 测试设计

- 测试必须使用真实代码与 mock 的 ctx / webServer / betterSidebar，避免启动真实宿主
- 一个测试只测一个行为，测试名描述期望行为（见测试规范 skill）
- 覆盖边界情况：空 path、非法 sessionId、损坏状态文件、LRU 上限裁剪、重复访问去重

## 测试覆盖率检查

> **行覆盖率 ≥ 85%，分支覆盖率 ≥ 75%**（新增代码增量覆盖）。

- 覆盖率统计针对 `plugins/<name>/lib/`（server 端 `index.js` 为主）
- 无内置覆盖率工具时，用 `node --experimental-test-coverage`（Node 20+）或 `c8` 生成报告
- 每次新增代码必须添加测试用例，提交前检查覆盖率达标

## 异常处理原则

> **任何测试异常都必须被处理，不得遗留。**

### 与当前修改无关的异常

- 如果测试过程中出现异常，但经确认**与当前代码修改无关**：
  1. 当前可以**只关注自己的修改**，继续完成当前任务
  2. 但**必须记录该异常**（记录到 `docs/踩坑/` 或提交一个 Issue）
  3. **事后必须及时修复**，不得无限期搁置
  4. **修复后更新踩坑记录**：对应条目状态改为「已解决」，添加一句话解决参考（≤ 100 字）

### 必须修复的异常

- 与当前修改直接相关的测试失败 → **必须先修复才能提交**
- 新引入的语法错误或依赖冲突 → **必须先解决**

## 发布到仓库

**双通道发布**：GitHub Release（tag 触发自动打包）+ npm 官方 registry（release.yml 自动 `npm publish`）。tag 格式：`<包名>@v<版本>`（如 `dsh-file-activity@v0.4.0`）。

发布流程详见 [发版流程](发版流程.md) 与 `.github/workflows/release.yml`：

1. `package.json` 版本递增（semver，推荐 `node scripts/release.mjs <插件名> --bump <patch|minor|major>`）
2. `CHANGELOG.md` 顶部加对应 `## [x.y.z]` 段落
3. `git tag <包名>@v<版本> && git push origin <包名>@v<版本>`
4. GitHub Actions 自动：校验插件目录与版本一致 → 跑测试 → `npm pack` 打 tarball → 创建 Release（附件 tarball + CHANGELOG 段落）→ npm 发布
