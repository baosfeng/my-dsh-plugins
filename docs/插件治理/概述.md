# 插件治理（dsh-my-guardian）

> ⚠️ **何时阅读：** 安装第三方/自研插件经常导致 DSH 启动失败时，或修改本插件代码前。

## 功能一句话

**新装/刚更新的插件先进"候选区"，由守护插件在 DSH 启动完成后逐个热挂载：成功自动转正，失败自动禁用并记录；对写进启动名册的插件做启动前静态预检并留痕，配套侧边栏诊断面板与安全模式。** 核心启动区只保留稳定插件，把"坏插件拖垮整个 DSH"的概率降到最低。

## 解决的问题

DSH（Cordis）插件加载是 all-or-nothing：启动时任何插件 import 失败 / apply 抛错 / 依赖缺失都会让整个 `dsh web` 起不来（fail-loud 退出）。本插件利用 loader 运行时动态挂载 API（失败可 catch、可回滚），把新插件延迟到启动后加载，实现业界通行的"隔离 + 兜底"：

- **两段式加载**（借鉴 VS Code 懒激活 / systemd 分级启动）
- **启动名册静态预检**（issue #144：覆盖"插件直接写进启动名册"的未兜住缺口，见下节）
- **失败自动禁用**（借鉴 VS Code 提示禁用问题扩展 / systemd 失败计数）
- **安全模式**（借鉴 VS Code `--disable-extensions` / IDE 安全模式）
- **诊断面板**（插件状态一览，人工处置入口）

## 工作机制

```
cordis.patch.yml（核心区，启动时加载，守护插件自身）
        ├─ 启动阶段：静态预检名册（issue #144）——包可解析 / peerDependencies / 重复 id
        │      └─ 发现的问题 → $DSH_HOME/guardian/startup-issues.json（不阻断启动）
        ↓ 新插件写进
cordis.staged.json（候选区）
        ↓ DSH 启动完成后
守护插件逐个依赖预检（peerDependencies）+ tree.create() 动态加载
        ├─ 成功 → 自动转正（移出候选区，进入 guardian 持久化清单，每次启动自动恢复）
        └─ 失败 → 自动隔离（disabled 记录 + 失败类型/依赖缺失/安装建议 + 事件日志）
              └─ 连续失败 3 次 → 冻结（需手动解除）
```

## 启动名册静态预检（issue #144）

两段式加载只能兜住"走候选区"的插件；**直接写进启动名册（cordis.patch.yml / profile 名册 / bundles）的插件仍由 DSH 启动时 all-or-nothing 加载**——任一条目失败整个 `dsh web` 起不来，守护自身（也是名册条目）无法在其后兜底。为此守护在自身 apply 后立即对名册做**静态**预检（不实际加载插件）：

| 检查项                | 为什么致命                                                          | 预检动作                                                         |
| --------------------- | ------------------------------------------------------------------- | ---------------------------------------------------------------- |
| 包可解析              | import 失败 → `assertEntriesLoaded` throw，启动失败                 | 名册中 `dsh-*` 插件的包必须在 profile node_modules 中存在        |
| peerDependencies 满足 | 依赖缺失在 import 阶段抛 MODULE_NOT_FOUND                           | 复用候选挂载预检（`lib/dep-precheck.js`），缺失/版本不满足即记录 |
| 无重复 entry id       | `EntryGroup.update` 对同一 group 配置抛 `duplicate loader entry id` | 全量条目 id 去重                                                 |

发现的问题条目写入 **`$DSH_HOME/guardian/startup-issues.json`**（原子写，名册健康也写空报告 + checkedAt），守护面板「最近事件」顶部**置顶**展示启动区问题，每条给出修复命令（`dsh plugin add ...`）与移除提示。**预检本身绝不阻断启动**（只记录、只告警）——最坏情况是名册有问题但守护仍尽力留下排查记录（apply 与坏条目的 import 并行执行，通常能抢在启动断言失败前写完报告）。

## 官方 all-or-nothing 行为调研（2026-09-06，issue #144）

对 `dsh-app-boot` / `cordis-plugin-loader`（deepseek-harness 仓库内 `@deepseek-ai/dsh-app-boot`、`@deepseek-ai/cordis-plugin-loader` 1.0.2）源码实证：

| 场景                                | 精确行为（源码位置）                                                                      |
| ----------------------------------- | ----------------------------------------------------------------------------------------- |
| 插件 import 失败                    | `assertEntriesLoaded`：`entry.fiber === void 0 && !entry.disabled` → throw，boot reject   |
| 插件 apply 抛错                     | `assertEntriesActivated`：`fiber.state === FIBER_FAILED` → 收集并 throw（保留原始堆栈）   |
| 插件 pending（依赖的 service 缺失） | `assertEntriesActivated`：`FIBER_PENDING` → 列出缺失 service 并 throw                     |
| 启动后未捕获异常                    | `installFailLoud`：`unhandledRejection` → 写诊断后 `exit(1)`                              |
| 名册重复 id                         | `EntryGroup.update`：同一 group 配置内 `seen.has(id)` → throw `duplicate loader entry id` |
| 运行中 HMR 失败                     | 宽容：警告 + 事务回滚旧树（不做启动断言）                                                 |

**唯一可用降级配置：条目 `disabled: true`**（写在名册配置里，支持 `!!js` 表达式计算；`entry.disabled` 使该条目不参与 loaded/activated 断言、不加载）。这是手动豁免——**官方没有"失败自动禁用并继续启动"（VS Code 式）的 fail-safe 机制**；启动失败后只有人工干预（删行 / 标记 disabled）。已建议官方在 `assertEntriesActivated` 增加可选的"失败自动禁用继续启动"行为（详见本 issue #144 评论中的提案点）。

## 业务场景映射

| 业务关键词                         | 入口与方法（源码路径）                                                                                                                                                              |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 候选插件加载 / 失败自动禁用 / 转正 | `plugins/dsh-my-guardian/lib/index.js`（server）— `apply()` 内 `scanStaged()` / `mountWithState()` / `processStagedEntry()`                                                         |
| 安全模式                           | `plugins/dsh-my-guardian/lib/index.js` — `state.safeMode` 读取与生效（挂载跳过 + 卸载已挂载）                                                                                       |
| 启动名册静态预检（启动区问题）     | `plugins/dsh-my-guardian/lib/startup-check.js`（server）— `runStartupCheck()` 于 apply 后执行；报告写 `$DSH_HOME/guardian/startup-issues.json`；面板置顶区块 + `startup-issue` 事件 |
| 诊断面板 / 状态列表 / 重试         | `plugins/dsh-my-guardian/lib/client.js`（client）— 侧边栏页签 + `/guardian/api/*`                                                                                                   |
| 状态文件                           | `$DSH_HOME/guardian/state.json`（原子写，损坏降级）                                                                                                                                 |

## 安装与使用

1. 仓库根 `pnpm install`
2. 在 `~/.dsh/profiles/<name>/cordis.patch.yml` 的 insert 列表**第一行**加：
   ```yaml
   - id: guardian
     name: 'dsh-my-guardian'
   ```
3. 新建候选文件 `~/.dsh/profiles/<name>/cordis.staged.json`，把新插件写进去（顶层数组 `{id, name, config}`）
4. 硬刷新浏览器 → 侧边栏出现"插件守护"页签

## 自身可靠性（看门狗自保）

守护插件自己必须先活着，否则一切治理都是空谈。为此：

- **apply 永不抛错**：最外层 try/catch 兜底，任何同步错误只降级（不治理）不崩溃（fail-loud 会 exit(1) 拖垮整个 `dsh web`）。
- **异步全路径 catch**：扫描/挂载/持久化/事件回调全部捕获，无 unhandledRejection。
- **API 延迟注册**：`webServer` 服务可能晚于守护插件挂载（loader 行并发激活），API 注册改为轮询补注册，不因时序竞态永久缺失（真实环境验证发现并修复）。
- **状态文件损坏降级**：`state.json` / `cordis.staged.json` / `startup-issues.json` 损坏时降级为空状态，不影响启动。
- **无第三方运行时依赖**：只用 Node 内置模块 + loader 公开 API，代码极薄。
- **自身出问题的恢复手段**：从 `cordis.patch.yml` 删掉 guardian 行即可恢复（候选插件本来就没激活，无残留）。

## 边界（重要）

- 进程级隔离需要 DSH 框架支持（worker/子进程 + RPC），本插件提供的是**加载时序与失败处置**的兜底隔离，不是资源隔离。
- 正式核心区（`cordis.patch.yml`）里的插件仍遵循启动 all-or-nothing。缓解手段：**启动名册静态预检**（上一节）在启动失败前留下 `startup-issues.json` 排查记录 + 面板置顶修复命令；官方唯一自动豁免是条目标记 `disabled: true`。请把一切新插件先放入候选区验证。

## 框架演进方向（远期，非本插件范围）

给 DSH 核心（`@deepseek-ai/dsh-app-boot` / `@deepseek-ai/cordis-plugin-loader`）的建议，供未来改进：

1. **启动失败不阻断（主动降级）**：将 `assertEntriesActivated` / fail-loud 改为"失败条目自动写 disabled 并继续启动"（VS Code 式）——坏插件只影响自己，不再拖垮整个 `dsh web`。当前基线：`entry.disabled` 是唯一豁免（已实证），但必须先手动标记；建议增加可选配置项（如 `loader.failSafe: 'quarantine'`）在启动断言失败时自动禁用失败条目并继续。**该建议已写入本 issue #144 的评论**（调研结论 + 提案点，供官方仓库跟进）。
2. **进程级隔离**：server 插件跑在 worker_threads / 子进程中，通过 RPC 通信（借鉴 VS Code Extension Host）；client 插件同理（iframe / 独立 bundle 边界）。
3. **失败计数与分级启动**：loader 内置"连续失败 N 次自动禁用 + 启动分级"能力，替代本插件的用户态实现。
