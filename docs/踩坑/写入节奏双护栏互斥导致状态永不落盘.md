# 写入节奏双护栏互斥导致状态永不落盘（issue #198 收尾）

## 症状

- 插件的状态文件**停留在旧内容**，进程内存里的最新状态**永远写不出去**；
- **没有任何异常**：不抛错、不 reject、测试里的断言只表现为「读到旧状态」；
- 唯一线索是日志里一条 warn：`[write-scheduler] write blocked N time(s) — dropping pending snapshot`（很容易被当噪音忽略）。

## 根因

`createWriteScheduler`（调度器）与 `atomicWriteJson`（快照护栏）**同时启用节流**时，节流窗口会互相打架：

```text
scheduler.schedule() → 到点 → write({ force: false })      ← drain()/普通调度都是非 force
   → atomicWriteJson(...) 命中自己的节流窗口（距上次写 < minIntervalMs）
   → 返回 false（被拒）
   → 调度器重排（默认 3 次），每次仍落在原语窗口内 → 再次被拒
   → 重排耗尽 → 放弃（dirty 清空 + 一条 warn）→ 内存状态再无机会落盘
```

关键判据：**调度器间隔 < 快照原语的节流窗口**（例：调度器 100ms + 原语默认 1000ms）→ 必然丢状态。
若两者窗口相同（都是 1000ms），调度器的推迟恰好覆盖原语窗口 → 不丢，但这是**巧合**，任一方调整间隔即退化。

## 判定（机械可检查）

- 出现 `createWriteScheduler` 的文件里，`atomicWriteJson` 调用**必须**带 `minIntervalMs: 0`；
- 反之，直接用 `atomicWriteJson` 的节流时，不要再套调度器。
- 契约定死：`plugins/dsh-shared/test/scheduler-throttle-conflict.mjs`（A2 = 丢状态反例；A1 = 巧合安全；B = 正确用法）。

## 修法

**写入节奏只能有一个来源**——用调度器就关节流（`minIntervalMs: 0`），节奏（防抖 + 最小间隔 + 串行）全交给 `createWriteScheduler`。

实测命中与修复（issue #198 收尾批）：

| 插件                                           | 修复前                  | 判定                 | 处理                      |
| ---------------------------------------------- | ----------------------- | -------------------- | ------------------------- |
| dsh-my-context                                 | 调度器 1s + 原语默认 1s | 巧合安全（脆弱）     | 统一为 `minIntervalMs: 0` |
| dsh-my-skill-manager                           | 调度器 1s + 原语默认 1s | 巧合安全（脆弱）     | 统一为 `minIntervalMs: 0` |
| dsh-my-guardian / dsh-my-memory / dsh-my-guard | —                       | 接入时即采用单一来源 | 无需修                    |

## 预防复发

- 有确定性回归测试（A2 用例：构造「调度器间隔 < 原语窗口」→ 断言状态丢失发生，A1/B 断言正确用法不丢）；
- README「写入节奏只能有一个来源」写进适用边界，可用 grep 机械检查；
