# 发版坑

## 症状关键词（可 grep）

- 远端 tag 齐全但 Actions **一个 run 都不触发**（批量推完 tag 后零 run，本地脚本却报成功）
- 同一 tag 同时出现 `Release` 与 `Release Optimized` 两个 run（一套发布被跑两遍）
- Release workflow 卡在 `softprops/action-gh-release` 步骤：`Error saving asset` / `Error creating asset temp dir` / `Error uploading` / 5 分钟后吐 `<!DOCTYPE html>`（HTML 错误页）
- Release workflow 的版本校验步骤失败：`tag version '<x>' does not match plugins/<插件> package.json version '<y>'`
- `lsof -ti :3087` 仍有进程、`/tmp/dsh-verify-real-*` 目录残留（父进程提前退出留下的孤儿实例）
- 并行发版时多个插件日志出现同一个端口号、两个实例互相踢
- `! [rejected] main -> main (fetch first)`（改了 `url` 没改 `pushurl`，`--push` 仍往 GitHub 推）

## 根因

- **tag 零触发**：一次 `git push` 带多个 tag ref（`git push origin t1 t2 … tN`）时，GitHub 对这批 ref 的 push 事件会合并/丢弃——**一次 push 只应承载一个 ref**。实测批量发版推完十几个 tag 后 2 小时以上零 run，只能人工逐个「删远端 tag → 稍等 ≥5s → 重推」。
- **Release 抢建**：`.github/workflows/` 里曾有两套 workflow 同源监听 `push: tags ['*@v*']`（`release.yml` 与 `release-optimized.yml`），同一 tag 两个 run **并发**调 `action-gh-release` 创建同一个 Release、上传同名 `<pkg>-<ver>.tgz`，互相删/建资产 → 报错或上传挂死。**交付物本身没丢**（另一个 run 通常已把 Release 建成），红的是这条 run。
- 版本校验比的是 tag 里 `@v` 之后的**裸版本**与 tag 指向 commit 的 `package.json` 版本：任一侧带 `v` 则任何 tag 都失败；另一形态是手动 bump 后**没提交**，tag 指向的 commit 里仍是旧版本。
- 并发改变的是**资源生命周期**：串行时天然成立的「某门禁失败就提前 return／kill」会让已启动的隔离实例变成孤儿（清理只在自身控制流里，没注册信号处理器）；各插件自探端口的探测—释放—启动窗口在并行时必然撞端口；git 推送时 `pushurl` 优先于 `url`。

## 修法

- **tag 逐个推**（固化在 `scripts/lib/release-tag-push.mjs` 的 `pushTagsIndividually`：一次 push 只带一个 ref）；推完逐个**确认触发**（`confirmTagTriggered`：查该 tag 下有没有 run），把静默零触发变成显式报错，并跳过注定落空的 post-release 干等。确认不到才用「删远端 tag → ≥5s → 重推」补救（`retriggerHint` 只打印命令，不代做删除）。
- **一个 tag 只留一套发布 workflow**：`release-optimized.yml` 已删（功能与 `release.yml` 重复，且其 matrix 只含一个元素）；`release.yml` 再加 `concurrency: group: release-${{ github.ref_name }}` 做同 tag 串行兜底。
- **判定交付物不看单个 run 的红绿**：Release 与 npm 是否到位才是判据（另一个 run 可能已经建成）。失败通知 issue 是症状，先核对交付物再决定重发。
- 手动 bump 后先提交再发版（或用 `--bump` 让脚本自动 bump + 提交）；校验失败后删旧 tag 重打重推。
- 并发启动的门禁**必须在返回前全部 await 完，失败路径也不例外，绝不 kill 它们**；端口由调度层预分配互不相同的值再传给各插件。
- 发版后校验**只等 GitHub Release**：Release 超时未创建即 exit 1，不许静默失败（`GH_TOKEN` 未配置才跳过，算 info）。npm 发布由 workflow 负责，本地**不轮询**——本机 npm 版本查询走镜像且缓存陈旧，实测既耗满 5 分钟超时窗口，又对**实际已发布成功**的包报「未在 5 分钟内发布」假警报（核对用官方源：`npm view <pkg> version --registry=https://registry.npmjs.org`）。
- 做 `--push` 的本地集成验证前先自检 `git remote get-url --push origin` 必须回显 bare 仓库路径；改指向时 `url` 与 `pushurl` 两个都改，否则「本地验证」会变成真实外发动作。

- `.github/workflows/release.yml`（版本校验 + 建 Release，同 tag 串行）、`.github/workflows/release-auto.yml`（批量入口）、`scripts/release.mjs`（tag 逐个推）
- `scripts/lib/release-tag-push.mjs`（逐个推 / 触发确认 / 补救命令）、`scripts/lib/post-release.mjs`（发版后校验：只判 Release，不轮询 npm）
