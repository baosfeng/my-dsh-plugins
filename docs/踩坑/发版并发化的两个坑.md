# 发版链路并发化的两个坑

issue #246（发版速度专项）把 `scripts/release.mjs` 从「严格串行」改成「流水线」时踩到的两处。
两处都不是「性能问题」，而是**并发改变了资源生命周期**——串行时天然成立的假设，并行时不成立。
另附③一条做集成验证时的 git 陷阱（也是实测踩到）。

## 坑 ①：并发门禁 + fail-fast 提前 return → 孤儿隔离实例

### 现象

把 1a（npm 查询）/ 3（插件测试）/ 3c（真实环境验证）改成并发后，如果沿用串行版的
「某个门禁失败就立刻 `return`」，进程会在 3c 还在跑的时候退出。后果：

- `node scripts/verify-real-profile.mjs` 启动的真实 DSH 实例**继续活着**，占着端口；
- 它创建的临时目录 `/tmp/dsh-verify-real-<端口>/` **不会被清理**；
- 下次发版换个端口启动 → 表面上成功，实际上机器上越积越多游离实例（正是
  [子agent工作区缺失导致卡死](子agent工作区缺失导致卡死.md) 那类"静默积攒"的形态）。

### 为什么

`scripts/verify-real-profile.mjs` 只在**自身控制流**里调 `cleanup()`（成功路径与它自己捕获的
失败路径），**没有注册 `SIGINT` / `SIGTERM` 处理器**。父进程提前退出时它拿不到任何通知，
既不会停实例也不会删临时目录。父进程主动 `child.kill()` 同样如此——所以"发现失败就杀掉在跑的门禁"
这个看起来很自然的选择，在这里是错的。

### 复现步骤

```bash
# 1. 让 3c 跑起来（约 10s），并在它跑的过程中杀掉父进程
node scripts/release.mjs <插件> &        # 或任何会启动隔离实例的调用
sleep 3 && pkill -f "verify-real-profile.mjs" && pkill -f "release.mjs"
# 2. 观察残留
lsof -ti :3087                            # 实例还在
ls -d /tmp/dsh-verify-real-*              # 临时目录还在
```

### 修法（已落地）

> **并发启动的门禁必须在返回前全部 `await` 完**，失败路径也不例外；**不要 kill 它们**。

`scripts/release.mjs` 里对应的两段代码都带注释说明：

- 静态门禁（1b-pre / 1b / 1c / 2 / 3b，实测 ~6ms）**先跑完**，失败时一个隔离实例都不会启动
  ——所以"失败时不能提前退出"并不会拖慢常见的失败路径（实测 484ms，比串行版 869ms 还快）；
- 静态门禁通过后才并发启动 1a/3/3c，然后**无条件 await 三者**再判定。

代价（诚实记录）：若 1a（版本防降级）失败，3c 已经跑起来了，要等它跑完（~10s）才退出。
这是刻意的取舍——多等 10s 远比留下孤儿实例可接受。

## 坑 ②：每个插件内部各自 `findFreePort(3087)` → 并行必然撞端口

### 现象

串行批量发版时三个插件先后用的是**同一个端口 3087**（实测日志可见），一切正常。
一旦并行，多个插件几乎同时调用 `findFreePort(3087)`：探测—释放—再启动之间存在窗口，
**多个插件会拿到同一个端口**，表现为"莫名其妙的实例启动失败 / 两个实例互相踢"。

### 复现步骤

```bash
# 串行版：三个插件顺序使用 3087（日志里逐个出现"端口 3087"）
node scripts/release.mjs a b c
# 并行版若沿用每插件内部 findFreePort：三行日志会出现同一个端口号
node scripts/release.mjs a b c --concurrency 3
```

### 修法（已落地）

端口由**调度层预分配**：`scripts/lib/release-checks.mjs` 新增 `findFreePorts(start, count)`，
按插件下标分配互不相同的端口（升序），再传给各插件的 3c。
单测：`scripts/test/release-ports.test.mjs`（含"已占用端口会被跳过"的断言）。

## 坑 ③：fork 里 `remote.origin.pushurl` 优先于 `url`，改 `url` 改不动推送目标

做 `--push` 流水线的**本地 bare-origin 集成验证**时踩到：把 `origin` 的 url 指向
`/tmp/gh-fake-origin.git` 后跑 `--push`，git 仍然往 `github.com` 推。

原因：本仓库的 fork 池约定给 `origin` 配了 `pushurl`（fetch 走 HTTPS、push 走 SSH），
而 **git 推送时 `pushurl` 优先于 `url`**。

修法：两个都改。

```bash
git remote set-url      origin /tmp/gh-fake-origin.git
git remote set-url --push origin /tmp/gh-fake-origin.git
git remote get-url --push origin      # 自检：必须回显 bare 仓库路径
```

**顺带的安全结论**：这次误推被 git 以 `! [rejected] main -> main (fetch first)` 拒绝，
没有对 GitHub 造成任何改动。但它提醒我们——**验证 `--push` 流水线之前，必须先自检
`git remote get-url --push origin`**，否则"本地验证"会变成真实外发动作。
