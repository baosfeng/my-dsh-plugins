# 超长单行让全仓正则扫描挂死

## 现象

新写的文档引用完整性校验脚本 `scripts/check-links.mjs`（扫描全仓 markdown 与文本行，校验链接、锚点、路径 token）首次接入时**挂死**：

```bash
$ node scripts/check-links.mjs
# 180 秒无任何输出（被外部超时杀掉）
```

没有报错、没有进度、没有 CPU 打满的明显信号——看起来像"卡在某个文件上"，但不知道是哪个。

## 根因

匹配 markdown 链接的正则被跑在**每一行**上，而仓库里有压缩产物与内联引擎的构建产物：

```
plugins/dsh-mermaid-render/lib/client.js           ← 单行 4.45 MB（base64 内联的 mermaid 引擎）
plugins/dsh-mermaid-render/vendor/mermaid.min.js   ← 最长单行 0.30 MB，另有 9 行 > 100k
```

对一条 4.45 MB 的行跑带多分支的链接正则（`!?\[[^\]]*\]\([^)]*\)` 这类），回溯成本随行长**平方级**增长 → 单行就耗掉几分钟到无限期。全仓 800+ 文件中只要有一行这种"压缩成一行"的产物，整个脚本就废了。

同类文件还有 `*-lib.js`、`*.min.js`、打包产物等，它们本来就永远不会包含需要校验的相对链接。

## 修法

在**匹配之前**做三重防护（顺序即成本从低到高）：

| 防护                  | 阈值                                   | 理由                             |
| --------------------- | -------------------------------------- | -------------------------------- |
| 排除压缩/打包产物路径 | `vendor/**`、`*.min.js`、`*-lib.js` 等 | 这类文件不承载被校验的引用       |
| 整体跳过超大文件      | > 1 MB                                 | 文档类文件不会有这个量级         |
| 跳过超长单行          | > 100 000 字符单行                     | 保留"大文件里混着正常文本"的场景 |

并配两条回归测试（构造超长单行 fixture 断言脚本仍在秒级完成），避免以后有人"优化"掉防护。

修复后同一仓库实测 **0.18 秒**扫完 876 个文件。

## 复查更正（2026-09-12，issue #185）

issue #185 复查插件体积时发现，上面"单行 8.9 MB"把**文件大小**与**单行长度**混了。实测口径：

| 文件                                                      | 大小        | 行数  | 最长单行      | >100k 字符的行 |
| --------------------------------------------------------- | ----------- | ----- | ------------- | -------------- |
| `plugins/dsh-mermaid-render/lib/client.js`（#185 缺陷态） | 8,934,938 B | 737   | **4,449,050** | 1              |
| `plugins/dsh-mermaid-render/lib/client.js`（#185 修复后） | 4,486,335 B | 740   | **4,449,050** | 1              |
| `plugins/dsh-mermaid-render/vendor/mermaid.min.js`        | 3,336,760 B | 2,030 | 302,842       | 9              |

两条结论：

1. **修复后 client.js 仍是 4.45 MB 单行，仍在"重灾区"**——三重防护必须继续覆盖
   `plugins/*/lib/**`（构建产物）与 `vendor/**`，不能因为体积减半就移除排除规则；
2. **现有保护够用，无需新增门禁**：#185 修复后实测 `node scripts/check-links.mjs` **0.21 秒**扫完
   883 个文件（校验 612 条引用、豁免 624 条），未挂死。产物同时被 `.prettierignore`
   （`plugins/*/lib/client.js`）、`eslint.config.js` ignores、`.jscpd.json`（`**/lib/client.js`）
   排除，`knip.json` 的 project glob 也不含 `lib/**`——扫描类门禁逐条都已排除。

→ 本坑的结论准确表述是「**按"单行长度"设阈值，而不是按"文件大小"**」，而不是"给某几个文件开白名单"：
`vendor/mermaid.min.js` 只有 3.3 MB（文件不算大），却仍有 9 行超过 100k 字符，继续印证"只看文件大小会漏"。

## 通用教训

**任何"扫全仓所有文本"的工具（链接校验、拼写检查、TODO 扫描、密钥扫描、正则重写），第一件事都是防压缩产物**——它们的特征是"单行超长"，而不是"文件大"。只按文件大小设限会漏（一个 500 KB 的 min.js 同样能让正则跪）；只按行数设限也会漏。**必须同时看单行长度。**
