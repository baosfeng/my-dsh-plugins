# 非交互默认放行导致真实触发

## 现象

某运维 CLI（skill 自带的写命令封装）在**非 TTY 且未给 `--yes`** 时执行写命令，只打印一行警告就真实触发了远端流水线运行：

```bash
$ ops pipeline run <pipelineId> < /dev/null     # 预期：拒绝执行
警告：该操作会真实改动远端数据 —— 触发流水线 <pipelineId>（分支 -，参数 {}）
已触发：流水线 <pipelineId>，runId 10            # ← 真实触发（盲测中实际发生一次）
```

而帮助文本承诺的是「`--yes` 跳过终端二次确认（**非交互环境必须**）」——**实现与承诺语义相反**。

## 根因

确认逻辑用 `and` 短路：非 TTY 时整段确认被跳过，直接落到 `return True` 放行。

```python
# 修复前
if not getattr(args, "yes", False) and sys.stdin.isatty():   # isatty()=False → 整段跳过
    if input("确认执行？") != "y":
        raise YxError("已取消")
return True                                                  # ← 非 TTY 静默放行
```

"非交互"被当成了"已同意"，而真实语义应当是"无法确认 ⇒ 拒绝"。

## 影响面

| 项         | 说明                                                                                                                   |
| ---------- | ---------------------------------------------------------------------------------------------------------------------- |
| 触发条件   | 非 TTY（`< /dev/null`、管道、`subprocess`、cron、CI）且未加 `--yes`                                                    |
| 受影响命令 | 写命令共 3 个：`pipeline run`（触发流水线，连带构建/部署）、`vars create`、`vars update`（改配置，影响所有关联流水线） |
| 实际损失   | 盲测中误触发 1 次流水线运行（runId 10，后 CANCELED），消耗构建资源；若流水线含部署步骤，后果更大                       |

## 修法（fail-closed）

两层防线：

1. **前置闸门 `gate_write(args)`**：在命令入口、**任何请求之前**判定——非 `--dry-run`、非 `--yes`、非 TTY → 立即报错退出，**零请求**（连读请求都不发，避免半途状态）。
2. **`confirm_write()` 同语义兜底**：`--dry-run` 只打印；`--yes` 执行；TTY 交互确认；其余拒绝。

| 调用场景               | 修复后行为                       |
| ---------------------- | -------------------------------- |
| 任意场景 + `--dry-run` | 只打印将发送的请求，永不改动数据 |
| 终端交互（TTY）        | 打印警告 + 输入 `y` 确认         |
| 非 TTY + `--yes`       | 执行                             |
| 非 TTY 无 `--yes`      | **拒绝执行，exit 1，零请求**     |

实测四种调用（`pipeline run`、`pipeline run --branch`、`vars create`、`vars update`）均拒绝：

```bash
$ ops pipeline run <pipelineId> < /dev/null; echo "exit=$?"
错误：非交互环境必须显式加 --yes（或先用 --dry-run 预演）；已拒绝执行，未发送任何请求
exit=1

$ ops pipeline run <pipelineId> --branch main --dry-run < /dev/null; echo "exit=$?"   # 预演始终安全
[dry-run] 未发送任何请求，远端数据未改动。
exit=0
```

顺序细节：`--params` 非法 JSON 等**本地参数校验先于闸门**（先告诉用户参数错），闸门先于一切网络请求（含 `--branch` 需要的流水线详情读取）。

## 防回归

skill 自带的 `selftest.py`（纯标准库、20 项、约 0.3s、零网络依赖）：以 stub 替换 `api()`，直接断言"被拒绝的写命令不得发送写请求"，**绝不触达真实服务**。

```bash
$ python3 selftest.py
Ran 20 tests in 0.293s
OK
```

测试有效性单独验证（防止"永远绿"的假测试）：把闸门换回旧逻辑的副本再跑同一套测试 → 3 项变红：

```text
旧逻辑副本测试结果：失败 3 项
测试有效性：✅ 能抓住缺陷（旧逻辑下变红）
```

## 原则

**破坏性能力默认拒绝（fail-closed）：非交互环境必须显式确认参数才放行，禁止"非交互 = 默认同意"。** 推论三条：帮助文本里的"必须"必须在实现里成立；拒绝要**零请求**；每条此类能力都要配防回归自测，并**验证测试能抓住旧行为**（换回旧逻辑应变红）。
