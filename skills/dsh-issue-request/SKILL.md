# 提需求为仓库 issue

## 概览

把用户的口头/模糊想法，变成自己仓库（`baosfeng/my-dsh-plugins`）上一条**规范、可开发、可验收**的 GitHub issue：澄清 → 防重复 → 现状调研 → 方案设计 → 起草 → 提交。**用户已授权直接执行，全程不再征询意见**（仅在需求方向确实无法推断时才追问一次）。

## 何时使用

- 用户提出新功能/体验改进诉求（"图标多彩一点""想支持 xxx""加个开关"）
- 想把一个想法正式登记为需求 issue（可追溯、可指派、可验收）
- 用户想整理/回顾仓库里的 issue

**不使用：** 开发/修改功能本身（用 `development-lifecycle`）；给官方仓库（deepseek-ai/deepseek-harness）提建议（目标仓库不同，先确认对方仓库的 issue 惯例）。

## 流程（按顺序执行，不可跳步）

### 0. 澄清需求

**默认不追问用户**（已授权直接执行）。表述缺信息时，优先通过第 2 步现状调研 + 上下文合理推断补齐；只有需求方向确实无法推断（会写错 issue）时，才用 `ask_user_question` 问一次。

按以下要点判断缺口并自行补齐：

- **形态**：期望怎么变（图标换样式 / 换颜色 / 加交互 / 加配置）——从用户原话提取
- **范围**：涉及哪个插件、哪些页面/列表（如"文件活动"里的统计列表、最近访问、浮窗预览）——从仓库结构推断
- **优先级**：用户未说明时不写优先级
- 有截图/参考例子更好；类型覆盖范围（只做点名类型还是常用类型配齐）——默认按常用类型配齐写进方案

### 1. 防重复（必做）

先搜已有 issue 是否已覆盖，**用多组关键词**（用户原词 + 同义词 + 英文，如 `图标`、`icon`、`颜色`、`多彩`、`文件活动`），按 `github-ops` 用 `ghops search issues`：

```bash
ghops search issues "repo:baosfeng/my-dsh-plugins <关键词>"
```

命中判定规则：

| 命中情况                               | 处理                                      |
| -------------------------------------- | ----------------------------------------- |
| open 且需求相同                        | 不重复开，贴已有 issue 链接，建议跟帖补充 |
| closed 且需求已实现                    | 告知用户已实现，不重复开                  |
| closed 但未实现（旧需求废弃/早期记录） | 直接开新 issue，正文注明"关联旧 issue #N" |
| 未命中                                 | 正常开新 issue                            |

### 2. 现状调研

- 对应插件源码：`plugins/<name>/`。**先 `ls` 确认结构再读**：server 端是 `lib/index.js`；client 端 `lib/client.js` **可能是构建产物**（由 `scripts/build.mjs` 拼接），源码在 `client.src.js` 或 `lib/parts/*.part.js`——不要改/引用构建产物当源码。
- 查重：先在 issue 列表搜索同类需求（已存在 → 告知用户，不重复开）。
- 确认现状事实（如"图标目前全部同色、不区分类型"），写进 issue 背景，不凭印象。

### 3. 方案设计（UI/交互类需求必做）

- 找可参考方案：网上图标集/配色（vscode-icons、devicon、file-icons、vscode-material-icon-theme、lucide file-type 等）、主流编辑器/IDE 配色惯例。
- 或自设计一套（给出颜色/图标对应表）。
- 给 **≥2 个方案 + 推荐理由**（含取舍：风格统一性、体积、依赖），写入 issue「建议方案」。

### 4. 起草 issue

- 标题前缀**遵循仓库既有惯例**（本仓库现有 issue 用 `[需求]` / `[建议]` / `[BUG]`；新需求统一 `[需求]`），标题格式为 `动词 + 对象 + 期望效果`，如 `[需求] 文件活动图标按文件类型多彩着色`。
- 正文按模板 `templates/issue-template.md`。

### 5. 提交前自查（不再征询用户意见）

用户已授权**直接提交，不再问确认**。提交前自查：

- 标题符合规范、正文模板字段齐全、验收标准可勾选
- 防重复已做、现状事实已核实、方案满足第 3 步要求（UI 类 ≥2 个方案 + 推荐理由）
- 自查通过 → 直接进入第 6 步提交

> 例外：仅当需求方向存在重大歧义且无法推断时，才先向用户澄清一次再提交。**拿不准宁可先问，不提交将就的草稿**——例如：提需求对象不明（不确定指哪个插件/页面）、需求与现状冲突、或含删除/破坏性语义时。

### 6. 提交

- **REQUIRED SUB-SKILL：** 按 `github-ops` 用 `ghops issue create baosfeng/my-dsh-plugins --title "..." --body "..."` 创建 issue（参数见 `ghops issue create --help`）
- 创建成功 → 把 issue 链接贴给用户

### 7. 联动

- 若用户提出要开发该需求 → 交给 `development-lifecycle`，由它在开发启动时把验收标准写进该 issue（issue 是需求与回归基准，本 skill 不代写）
- 若命中旧 issue（closed 未实现）→ 按第 1 步规则标注关联

## 标题与正文规范

| 项   | 规范                                                                |
| ---- | ------------------------------------------------------------------- |
| 标题 | `[需求] <动词> + <对象> + <期望效果>`；不用"优化一下""改进"等空泛词 |
| 背景 | 现状是什么、哪里不满足、影响谁                                      |
| 期望 | 改完后用户看到什么                                                  |
| 方案 | ≥1 个具体方案（含取舍依据），UI 类给图标/配色方案                   |
| 验收 | 可勾选清单（`[ ]` 项），能验证是否完成                              |
| 附件 | 截图/设计/参考链接，用 Markdown 嵌入或粘贴链接                      |

## 常见错误

| 错误                     | 解法                                             |
| ------------------------ | ------------------------------------------------ |
| 重复 issue               | 第 1 步多关键词搜索必做                          |
| 命中 closed issue 不判断 | 按判定表区分"已实现 / 废弃"                      |
| 标题空泛（"优化一下"）   | 动词+对象+效果                                   |
| 没有验收标准             | 模板必填                                         |
| 反复征询用户意见         | 用户已授权直接执行，仅在无法推断的重大歧义时才问 |
| 把构建产物当源码         | 先 ls，client.js 可能是 build 产物               |
| 混入开发流程             | 本 skill 只做登记，开发走 development-lifecycle  |
